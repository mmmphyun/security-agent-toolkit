# 프로젝트 회고 Part 5: 비정형 텍스트 파싱의 한계 극복과 동적 메타데이터 기반 대량 동기화

## 1. 프로젝트 시작 배경 및 문제 정의 (Why)

### 1.1. 웹 어드민 대신 '디스코드 쓰레드'를 고수한 이유
80개 이상의 직업 설명, 스킬 수치, 패치노트, 일러스트, 그리고 수백 명 유저의 닉네임 데이터를 위키 웹에 적재해야 했다. 일반적인 웹 서비스라면 정형화된 입력 폼(Web Admin Form)을 만드는 것이 개발자 관점에서는 가장 안전하고 단순한 접근이다. 그러나 운영 관점에서 이를 기각했다:
- **운영 환경의 파편화 방지:** 관리자의 모든 일상 업무, 유저 소통, 기획 회의는 이미 디스코드 안에서 완결되고 있었다. 웹 어드민을 분리할 경우 "디스코드에서 논의하고 웹에 복사하는" 이중 작업과 플랫폼 전환 비용이 발생했다.
- **기존 데이터 자산 보존:** 수년간 디스코드 채널과 쓰레드에 누적된 방대한 세계관 텍스트를 다른 플랫폼으로 수동 이관하는 작업은 운영진에게 막대한 피로도를 유발했다.
- **단일 운영 인터페이스:** 디스코드를 단일 진실 공급원(SSOT)으로 유지하고, **"운영자가 쓰던 마크다운 쓰레드 작성 방식을 그대로 보존하되 백엔드 파서가 이를 정형 데이터로 변환하는 파이프라인"**을 구축하기로 결정했다.

### 1.2. 비정형 텍스트가 불러온 세 가지 엔지니어링 난관
1. **단순 키워드 검색의 한계:** 직업 설명 본문에 세계관 스토리(Lore)가 길어지면서, 분류용 단어가 스토리에 우연히 포함되어 발생하는 오탐(False Positive).
2. **도메인 확장에 따른 규칙 파편화:** 시스템이 업데이트되면서 직업의 제약 조건(1인 제한, 2차 각성 등)이 계속해서 늘어나는 도메인 확장성 문제.
3. **가변적인 유저 닉네임 구조:** 길드 유무, 역할 유무에 따라 구분자(`ㅣ`)의 개수와 위치가 제각각인 유저 닉네임을 안정적으로 분해해야 하는 문제.

## 2. 텍스트 파서의 진화: 키워드 검색에서 구조화 문법으로

### 2.1. 영웅/빌런 분류의 엣지 케이스와 메타데이터 브래킷 도입
- **초기 구현의 실패:** 초기에는 직업 설명 본문 텍스트 내에 "영웅" 또는 "빌런"이라는 단어가 존재하는지 단순 문자열 검색을 수행했다.
- **발생한 결함:** 직업 배경 스토리에 *"과거에는 영웅이었으나 타락하여 빌런이 되었다"*와 같은 서사가 들어가면 두 단어가 모두 매칭되어 잘못된 진영으로 분류되거나 파서가 충돌했다.
- **해결책 (`src/bot/utils/text_parser.py:41-48`):**
  본문 탐색을 폐기하고, 제목/헤더 영역에 `[영웅]`, `[빌런]` 형태의 **명시적 메타데이터 브래킷 문법**을 정의했다. 정규식 `re.findall(r"\[(.*?)\]", desc_str)`을 통해 브래킷 내부의 지정된 키워드만 엄격히 추출함으로써 서사 텍스트와의 간섭을 완벽히 격리했다.

### 2.2. 제약 조건의 일반화: 하드코딩에서 범용 캡슐화(`<< >>`)로
- **초기 구현:** 초기에는 "1인 제한" 직업만 존재했기에 단순 문자열 포함 여부(`'1인 제한' in text`)만 플래그(`is_limit = 'Y'`)로 처리했다.
- **도메인 확장:** 기획이 고도화되면서 "2차 각성 필요", "전직 퀘스트 완료", "히든 직업" 등 다양한 형태의 제약 조건이 추가되기 시작했다. 하드코딩 조건문으로는 감당할 수 없었다.
- **해결책 (`src/bot/utils/text_parser.py:51-56`):**
  `<< 조건문 내용 >>` 형태의 범용 캡슐화 태그를 도입했다. 정규식 `re.search(r"<<(.*?)>>", desc_str)`로 태그 내부의 문자열을 추출하여 `req_condition` 메타데이터로 분리 적재하고, DB 설명 컬럼에는 본문만 남기도록 태그를 제거하는 전처리 파이프라인을 구축했다.

### 2.3. 단일 패스(Single-pass) 상태 머신 파서 (`_flush_job`)
하나의 거대한 정규식으로 전체 문서를 파싱하면 마크다운 줄바꿈이나 공백 차이로 인해 정규식 역추적(Catastrophic Backtracking)이 발생하거나 파싱이 실패하기 쉽다.
- **라인 단위 순회와 컨텍스트 스택:**
  문서를 줄 단위로 읽으며 `## 게이트명`, `### 직업명`을 만날 때마다 현재 컨텍스트를 갱신했다.
- **버퍼 배출 패턴 (`_flush_job`):**
  새로운 직업 헤더를 만나거나 문서 끝에 도달했을 때만 누적된 설명 라인들을 합쳐 코스트 키워드(기력, 마나, 체력, 에너지) 추출, 태그 파싱, 공백 제거 고유 ID 생성을 완료하고 DB 엔티티로 배출하는 단일 패스 상태 머신을 완성했다.

### 2.4. 표준 AST 파서 대신 커스텀 파서를 구현한 이유
마크다운 파싱을 위해 `mistletoe`나 `Python-Markdown` 같은 검증된 AST(Abstract Syntax Tree) 파서 라이브러리를 사용하는 방안도 검토할 수 있었다. 그러나 두 가지 실무적 이유로 커스텀 파서를 선택했다:
- **저사양 VM 의존성 최소화(Zero External Dependency):**
  GCP 프리티어(e2-micro)의 극도로 제한된 자원(RAM 1GB 미만) 환경에서 외부 의존성을 늘리지 않고 파이썬 표준 라이브러리(`re`, `split`)만으로 경량 구동하기 위함이었다.
- **도메인 메타데이터 추출의 직접성:**
  표준 AST 파서는 정형 마크다운 태그를 분석하는 데 적합하지만, 본 프로젝트의 핵심은 마크다운 본체보다 그 안에 포함된 `[영웅/빌런]`, `<< 1인 제한 >>`, 코스트 키워드 같은 **비표준 도메인 메타데이터의 추출**이었다. AST 트리를 생성한 뒤 2차 순회를 도는 것보다, 라인 순회 단일 패스 상태 머신으로 한 번에 처리하는 것이 코드 복잡도와 메모리 오버헤드 면에서 훨씬 직관적이었다.

## 3. 닉네임 대량 동기화(Bulk Sync)와 동적 템플릿 설계

### 3.1. 가변 닉네임 구조 파싱 시 고려했던 세 가지 대안
수백 명의 유저 닉네임(`display_name`)은 `[길드] 닉네임 ㅣ 역할 ㅣ 직업` 또는 `닉네임 ㅣ 직업` 등 구분자(`ㅣ`) 개수와 위치가 유저 상태에 따라 달랐다.

| 대안 | 검토 내용 | 기각/채택 사유 |
| :--- | :--- | :--- |
| **1. 화이트리스트 기반 매칭** | 80여 개 직업명과 길드명 목록을 메모리에 올리고 문자열 매칭 | 직업명 개정 및 신규 길드 생성 시마다 화이트리스트를 재동기화해야 하는 관리 비용 과다로 **기각** |
| **2. 로컬 경량 AI(NLP) 파싱** | SLM이나 개체명 인식(NER) 모델을 파이프라인에 배치 | GCP 프리티어 저사양 VM의 극심한 메모리(RAM) 및 CPU 제약으로 인해 호스팅 불가하여 **기각** |
| **3. 명령어 기반 동적 포맷 템플릿** | 슬래시 명령어로 유효한 닉네임 구조(인덱스 매핑)를 등록하여 검증 | 인프라 추가 비용 0원, 관리자 자율성 확보, 결정론적 검증 가능하여 **최종 채택** |

### 3.2. 동적 닉네임 양식 설정 (`set_nickname_format`)
- **관리자 설정 커맨드 (`src/bot/cogs/system/nickname_format_cmd.py`):**
  운영진이 슬래시 명령어 `/닉네임양식설정`을 통해 서버 내에서 통용되는 닉네임 구조를 DB에 등록할 수 있도록 했다:
  - `part_count`: 구분자로 분리했을 때의 총 조각 개수 (예: 3)
  - `nickname_index`: 실제 한글 닉네임의 위치 (1-based)
  - `job_index`: 직업명의 위치 (1-based)
  - `delimiter`: 구분자 문자 (기본값: `ㅣ`)
  - `staff_index`: 스태프 역할 식별자 위치 (선택)

### 3.3. 대량 동기화 배치 파이프라인과 실패 리포트 옵저버빌리티 (`bulk_sync_cmd.py`)
- 관리자가 `/유저동기화` 명령어를 실행하면 봇이 길드 내 전체 멤버를 순회한다.
- **Fail-Safe 필터링 (`bulk_sync_cmd.py:41-55`):**
  특수 이모지(`🌈`)나 접두사(`STF`, `stf`)를 1차 정제한 후, 등록된 포맷 템플릿들 중 일치하는 `part_count`가 하나도 없는 비정상 닉네임은 DB 적재 대상에서 즉시 제외하여 DB 오염을 차단했다.
- **실패 사유 투명 리포팅 (`bulk_sync_cmd.py:74-82`):**
  '조용한 누락(Silent Drop)'으로 인한 관리 사각지대를 방지하기 위해, 동기화 완료 시 **성공 건수뿐만 아니라 매칭에 실패한 유저의 닉네임, Discord ID, 실패 사유(`reason`)를 최대 15명까지 디스코드 채널로 실시간 리포팅**했다. 관리자는 이 리포트를 보고 양식을 어긴 유저에게 수정을 안내할 수 있었다.

## 4. 인제스터 탐색 힌트 (Key Modules & Functions)

- **텍스트 파서 유틸리티:** `src/bot/utils/text_parser.py`
  - `parse_job_descriptions`: `_flush_job` 패턴의 마크다운 상태 머신 파서, 코스트/타입/제약조건 추출.
  - `parse_job_patches`: 패치노트 마크다운 구조화 파서.
  - `parse_user_nickname`: 등록된 템플릿 기반 동적 닉네임 파서.

  - `sync_users_command`: 서버 전체 유저 닉네임 필터링, DB 배치 업서트 및 실패 리포트 전송.
  - `sync_jobs_to_db`: 직업 파싱 데이터베이스 일괄 동기화.

## 5. 결과 및 엔지니어링 교훈 (Results & Lessons Learned)

1. **사용자의 업무 맥락을 보존하는 엔지니어링:**
   개발 편의를 위해 정형 폼을 강제하기보다, 운영자의 기존 작업 환경(디스코드 쓰레드)을 지켜주면서 백엔드 파서로 데이터를 정형화한 선택이 조직의 마찰을 없앤 핵심 성공 요인이었다.
2. **도메인 확장에 대비한 문법(Grammar) 설계:**
   단순 키워드 검색은 세계관 텍스트가 풍부해질 때 반드시 깨진다. 브래킷(`[ ]`)과 컨테이너(`<< >>`) 같은 명시적 메타데이터 문법을 도입하여 비즈니스 로직과 서사 데이터를 격리해야 한다.
3. **ReDoS와 정규식 안정성에 대한 기술 부채 인식:**
   당시에는 도메인 규칙 확장에 집중하느라 정규식 엔진의 백트래킹(ReDoS) 취약점까지는 선제 방어하지 못했다. 비정형 입력을 다루는 파서에서는 텍스트 길이 제한(`max_length`)을 엄격히 두거나, 백트래킹이 없는 정규식 엔진(Google re2) 도입을 고려해야 함을 배운 중요한 기술적 교훈이었다.
4. **옵저버빌리티가 결합된 방어 프로그래밍:**
   잘못된 데이터를 단순히 버리는 것(Silent Drop)에 그치지 않고, 실패한 유저와 사유를 관리자에게 투명하게 리포팅해야 시스템의 신뢰성과 운영 지속성이 보장된다.
