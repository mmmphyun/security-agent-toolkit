# 프로젝트 회고 Part 2: 실시간 분산 동기화의 기술적 난관과 현장 중심의 트러블슈팅

## 1. 데이터 무결성 방어와 옵저버빌리티(Observability) 구축

### 1.1. 조용한 실패(Silent Failure)의 딜레마
디스코드 텍스트를 파싱하여 DB에 적재하는 파이프라인에서 가장 경계한 것은 **"잘못된 포맷의 데이터가 DB를 오염시키는 것"**이었다.
- **초기 방어 설계:** 정규식 파싱이 실패하면 DB 트랜잭션을 실행하지 않고 에러 로그만 터미널에 남긴 뒤 무시하는 방어적 로직을 적용했다.
- **운영상의 한계:** 데이터 오염은 막았으나 '조용한 실패(Silent Failure)'로 인해 운영자는 파싱이 누락되었음을 인지하지 못했고, 개발자는 문제 원인을 파악하기 위해 매번 GCP VM에 SSH로 접속해 `docker logs`를 수동 추적해야 하는 심각한 디버깅 병목이 발생했다.

### 1.2. 관제 알림(Alerting) 체계 구축 및 AI 보정 도입 폐기 이유
- **관제 채널 기반 실시간 Alerting:**
  도커 컨테이너 내부의 심각한 런타임 오류 및 봇의 파싱/동기화 작업 실패 이벤트를 감지하여, 스택트레이스 및 실패 원인을 디스코드 관리자 전용 관제 채널로 즉각 전송하도록 개선했다. 이를 통해 SSH 접속 없이도 실패 원인을 실시간으로 파악할 수 있는 최소한의 옵저버빌리티를 확보했다.
- **AI 자동 교정 API 도입 검토 및 폐기 (Safety & Determinism):**
  운영자의 비정형 글을 LLM API로 재가공하여 파서에 넣는 방안을 검토했으나 폐기했다. 타인이 작성한 도메인 설정과 수치 데이터가 AI의 환각(Hallucination)이나 임의 요약으로 왜곡될 위험이 있었기 때문이다. **"자동화의 편리함보다 데이터의 정확성과 결정론적 무결성"**을 우선시하여 명시적 에러 피드백을 주고 사람이 수정하도록 유도했다.

## 2. 실시간 화이트리스트 동기화: 메시징 아키텍처와 사설망 보안

### 2.1. 직접 소켓 통신 대신 Redis Pub/Sub을 선택한 이유
디스코드 음성 통화방(Voice Channel)에 접속 중인 유저만 인게임(Minecraft) 접속을 허용하는 실시간 화이트리스트 기능 요구가 발생했다.

```
[Discord User Voice Connect/Disconnect]
                  │
                  ▼
         [Discord Bot (Publisher)]
                  │
                  │ (Publish: player_whitelist_update)
                  ▼
         [Redis Broker (GCP / Docker)]
                  │
                  │ (Tailscale WireGuard Encrypted Mesh VPN)
                  ▼
   [Minecraft Server (Subscriber Plugin)] ──> [In-game Whitelist Memory / Kick]
```

- **직접 TCP/WebSocket 소켓 통신 검토:**
  - 초기에는 봇과 마인크래프트 플러그인 간 1:1 소켓 통신을 고려했다.
  - 하지만 양방향 연결 관리, 세션 유지, 재연결 핸들링 등 소켓 서버의 보일러플레이트 코드가 증가하여 빠른 릴리즈를 원하는 요구사항에 부합하지 않았다.
- **Redis Pub/Sub을 통한 느슨한 결합(Decoupling):**
  - 이미 캐싱 용도로 인프라에 상주하던 Redis를 메시지 브로커로 재활용했다.
  - Discord Bot(Publisher)과 Game Plugin(Subscriber)이 서로의 물리적 IP나 포트를 몰라도 Redis 토픽을 통해 비동기로 통신할 수 있어 컴포넌트 간 결합도를 낮추고 개발 속도를 대폭 단축했다.

### 2.2. Redis Pub/Sub의 한계(메시지 유실)와 자가 치유(Self-Healing) 설계
- **문제점 (Fire-and-Forget):**
  Redis Pub/Sub은 인메모리 기반의 단순 브로드캐스트 모델이므로 메시지 영속성(Persistence)이나 수신 확인(ACK)을 보장하지 않는다. 플러그인이 재시작되거나 네트워크가 일시 단절되면 퇴장 이벤트가 유실되어 '통화방을 나갔음에도 게임에 남아있는 정합성 불일치'가 발생할 수 있었다.
- **해결책 (주기적 재동기화 및 헬스체크):**
  이벤트 드리븐 방식의 실시간 Pub/Sub 통신 외에도, 주기적으로 디스코드 음성방 접속자 목록 스냅샷을 브로드캐스트하여 마인크래프트 서버의 화이트리스트 상태를 덮어쓰는 자가 치유(Periodic Re-sync/Self-Healing) 로직을 병행 구축해 상태 정합성을 보장했다.

### 2.3. 가변 IP 및 비전문가 환경을 극복한 Tailscale Mesh VPN
- **배경:** 게임 서버가 고정 IP를 가진 전용 IDC가 아니라, 비개발자인 서버장의 로컬 개인 PC(가변 IP, 공유기 NAT 환경)에서 구동되고 있었다.
- **포트포워딩의 보안 위험 차단:**
  서버장에게 공유기 포트포워딩을 요청할 경우 외부 침입에 노출되는 보안 홀이 생길 우려가 있었고, 수시로 바뀌는 공인 IP를 추적하는 동적 DNS 로직도 유지보수 비용이 컸다.
- **WireGuard 기반 Tailscale 도입:**
  포트포워딩 없이 NAT를 통과(NAT Traversal)하고, GCP 인스턴스와 로컬 PC를 1:1 종단간 암호화된 가상 사설망(Overlay Mesh Network)으로 묶었다. 이를 통해 공인망에 포트를 노출하지 않고도 안전하고 고정된 내부 가상 IP 기반의 통신 경로를 확보했다.

## 3. 요구사항 엔지니어링과 조직 변화 관리 (Change Management)

### 3.1. "알아서 해주세요"의 모호함을 깬 도그푸딩(Dogfooding)
- **문제 상황:**
  기능 기획 단계에서 클라이언트(서버장)에게 페인포인트와 요구사항을 지속 인터뷰했으나, "알아서 두루뭉술하게 해달라"는 소극적 피드백으로 인해 구체적인 스펙을 확정하기 어려웠다.
- **직접 현장 투입을 통한 문제 정의:**
  기획서 작성을 멈추고 **개발자가 직접 2~3주간 관리자 실무 업무에 투입(Dogfooding)**되었다. 유저 응대, 수동 직업 설명, 규칙 공지 등을 몸소 수행하며 관리자 입장에서 가장 피로도가 높은 반복 패턴을 스스로 식별하고 개선 스펙으로 변환했다.

### 3.2. 자립 가능한 시스템 구축과 버스 팩터(Bus Factor) 대응
- **비개발자 운영진을 위한 친절한 인터페이스:**
  명령어 사용법과 트러블슈팅 가이드를 비개발자 눈높이에 맞춰 상세히 문서화하고 관리자 전용 채널에 아카이빙했다.
- **온보딩 세션 의무화:**
  모든 운영진이 최소 1회 이상 직접 디스코드에 글을 올려 파싱 및 동기화를 수행해보는 실습 과정을 거치도록 했다. 이를 통해 개발자가 자리에 없어도 시스템이 중단 없이 자립적으로 운영되는 구조(Bus Factor 최소화)를 확립했다.

## 4. Part 2 결론 및 엔지니어링 교훈

1. **옵저버빌리티의 중요성:**
   데이터 오염을 막는 방어적 로직만큼이나, 시스템 내부의 실패를 투명하게 드러내는 관제와 알림 체계가 운영 비용을 결정한다.
2. **도메인 특성에 맞춘 기술 조합:**
   이미 존재하는 컴포넌트(Redis)의 숨은 기능을 활용하고, 네트워크 보안 도구(Tailscale)를 적재적소에 조합하여 복잡한 분산 환경 문제를 최소한의 공수로 해결했다.
3. **요구사항은 인터뷰가 아닌 현장에서 나온다:**
   모호한 클라이언트 앞에서는 탁상공론식 질문보다 직접 사용자의 업무를 경험(Dogfooding)하며 실질적인 병목을 발굴하는 주도성이 프로젝트의 성공을 좌우한다.
