# 프로젝트 회고 Part 1: 소규모 RPG 서버의 운영 병목에서 시작된 분산 아키텍처 설계

## 1. 프로젝트 시작 배경 및 문제 정의 (Why)

### 1.1. 소규모 서버가 마주한 현실적인 운영 병목
동시 접속자 20명 안팎의 소규모 마인크래프트 스토리 RPG 서버는 80개 이상의 방대한 직업군과 독자적인 세계관 시스템을 보유하고 있었다. 시스템의 깊이는 매력적이었으나, 운영 구조는 심각하게 비효율적이었다.
- **수동 1:1 온보딩의 한계:** 신규 유저가 유입될 때마다 관리자가 직접 일정을 잡고 음성/텍스트로 서버 규칙, 시스템, 80여 개 직업을 1:1로 설명하는 온보딩 과정을 거쳤다. 유저 유입이 늘어날수록 관리자의 운영 리소스가 온보딩에 매몰되는 구조적 병목이 발생했다.
- **정보 파편화와 높은 진입 장벽:** 80개 이상의 직업 정보가 디스코드 텍스트 채널에 흩어져 있어, 신규 유저는 직업을 탐색하고 선택하는 데 과도한 피로감을 느끼고 이탈했다.
- **기존 데이터 이관 및 단일 진실 공급원(SSOT) 부재:** 커뮤니티의 모든 활동과 데이터가 디스코드에 누적되어 있었기 때문에, 별도 웹사이트를 만든다 해도 운영자가 양쪽 플랫폼에 중복 입력해야 한다면 데이터 불일치와 관리 피로가 발생할 수밖에 없었다.

### 1.2. 엔지니어링 목표 정의
1. **온보딩 프로세스 자동화:** 규칙 설명과 직업 탐색을 웹 기반 가이드로 이관하고, 가이드 완수 여부에 따라 디스코드 역할과 권한을 자동 부여하여 관리자 개입을 최소화한다.
2. **Discord to Web 단방향 동기화 파이프라인 구축:** 기존 운영진의 업무 환경인 디스코드를 단일 진실 공급원(SSOT)으로 유지하되, 봇과 정규식 파서를 통해 데이터가 웹 위키로 자동 반영되는 파이프라인을 구축한다.
3. **비용 제로(Zero-cost) 기반의 고성능 분산 인프라 수립:** 제한된 예산 환경에서 클라우드 프리티어와 오픈소스 기술을 조합하여 지연시간과 부하를 극복하는 아키텍처를 설계한다.

## 2. 주요 설계 의사결정 및 기술 스택 선정 (Architecture & Trade-offs)

### 2.1. 애플리케이션 스택: 언어 일관성과 생산성
- **Discord Bot (Python `discord.py`):**
  풍부한 생태계와 레퍼런스를 보유한 `discord.py`를 선택하여 봇 개발 생산성을 확보했다.
- **Web Backend (Python `FastAPI`):**
  봇과 동일한 파이썬 런타임을 공유함으로써 도메인 모델과 유틸리티 로직의 재사용성을 높였다. 비동기 I/O 처리에 강점이 있는 FastAPI를 통해 위키 조회 요청을 경량으로 처리하도록 구성했다.
- **Database (PostgreSQL via Supabase):**
  유저-직업, 직업-무기-스킬 등 엔티티 간의 관계가 명확히 정의되는 도메인 특성상 관계형 데이터베이스(RDB)가 필수적이었다. 초기 셋업 공수와 운영 복잡도를 낮추기 위해 관리형 PostgreSQL인 Supabase를 채택했다.

### 2.2. 운영자를 배려한 '단방향 파이프라인' 아키텍처
새로운 웹 어드민 툴을 만들어 제공하는 대신, **"디스코드 → 웹" 단방향 파이프라인**을 고수했다.
- **조직 변화 관리(Change Management) 최소화:**
  이미 디스코드에 익숙한 운영진에게 새로운 웹 관리자 페이지를 학습시키는 것은 높은 비용을 수반한다.
- **단일 인터페이스 유지:**
  운영자는 평소처럼 디스코드 채널에 지정된 포맷으로 업데이트 글을 작성하거나 봇 명령어를 실행하기만 하면, 백엔드 파이프라인이 이를 파싱하여 DB와 웹 위키에 실시간 반영하도록 설계했다.

## 3. 인프라의 단계적 진화: 현실적 제약 조건 극복 과정

처음부터 모든 인프라를 완벽히 갖추고 시작하지 않았다. 서비스를 배포하고 운영하며 직면한 세 가지 현실적 병목(비용, 물리적 지연시간, 에셋 대역폭)을 해결하는 과정에서 인프라가 진화했다.

```
[운영자 / 유저]
       │ (업데이트 텍스트 / 명령어)
       ▼
[Discord Server] (SSOT)
       │
       │ (이벤트 수신)
       ▼
[Discord Bot (discord.py)] ──(Regex Parsing)──┐
       │ (FastAPI & Internal Logic)            │
       ▼                                       ▼
[GCP Compute Engine (Docker)] ──(Read/Write)──> [Supabase (PostgreSQL)]
       │                                               │
       ├──(Hot Data Caching)──> [Redis (Local In-Memory Cache)]
       │
       └──(Asset Offloading)──> [Cloudflare R2] (직업/무기 이미지 저장)
                                       │
                                       ▼
                               [Cloudflare CDN]
                                       │ (Edge Caching / DNS)
                                       ▼
                                [Web Wiki Client]
```

### 3.1. 컨테이너화 및 호스팅 (Docker & GCP)
- 환경 일관성과 무중단 운영을 위해 초기부터 모든 컴포넌트를 Docker 컨테이너로 격리했다.
- 상시 구동을 위한 클라우드 인스턴스로 GCP Compute Engine(프리티어/크레딧 활용)을 선택하여 호스팅 비용을 통제했다.

### 3.2. 물리적 네트워크 지연시간과 DB 커넥션 풀 고갈 → `Redis` 도입
- **원인:** GCP 인스턴스(미국 리전 등)와 DB(Supabase) 간의 물리적 거리로 인해 왕복 네트워크 지연시간(RTT)이 발생했고, 위키 트래픽 증가 시 DB 커넥션 풀 고갈 현상이 발생했다.
- **해결:** 읽기 비중이 압도적으로 높은 위키 서비스의 특성을 활용하여 **Redis 캐싱 레이어**를 도입했다. 자주 조회되는 직업/스킬 메타데이터를 인메모리에 캐싱하여 DB 직결 쿼리를 대폭 차단하고 응답 속도를 개선했다.

### 3.3. 스토리지 용량 한계와 로딩 속도 저하 → `Cloudflare R2 + CDN` 도입
- **원인:** 80여 개 직업 및 장비의 고용량 이미지를 Supabase 기본 스토리지에 저장하기에는 용량 제한이 있었고, 이미지 서빙 시 Egress 비용과 지연시간이 문제가 되었다.
- **해결:** 대용량 정적 이미지를 **Cloudflare R2 Object Storage**로 완전히 분리하고, 도메인 앞단에 **Cloudflare CDN**을 연동했다. Egress 비용 0원 혜택을 취하면서 엣지 캐싱을 통해 전 세계/국내 어디서든 즉각적인 이미지 렌더링이 가능하도록 최적화했다.

## 4. 인제스터 탐색 힌트 (Key Modules & Functions)

- **핵심 모듈 및 파이프라인:**
  - `bot/cogs/parser.py`: 디스코드 메시지에서 직업/스킬 데이터를 추출하는 정규식 파서 로직.
  - `api/routers/wiki.py`: Redis 캐시 히트/미스 전략이 적용된 위키 조회 엔드포인트.
  - `core/cache.py`: Redis 커넥션 관리 및 캐시 무효화(Invalidation) 헬퍼.
- **인프라 설정:**
  - `docker-compose.yml`: App, Bot, Redis 컨테이너 오케스트레이션 구성.

## 5. Part 1 결론 및 다음 편 예고 (Hook)

소규모 서버의 운영 비효율을 해결하기 위해 시작된 이 프로젝트는 **"단순 웹 제작"이 아닌 "운영자의 워크플로우를 보존하면서 분산 환경 간 데이터를 엮는 엔지니어링 문제"**로 발전했다.

비용과 물리적 인프라의 한계 속에서 Docker, Redis, Cloudflare R2를 단계적으로 도입하며 안정적인 서비스 기반을 마련했다.

그러나 실제 개발과 운영을 진행하면서 시스템은 더 까다로운 기술적 난관들을 마주하게 되었다:
1. **비정형 텍스트 파싱의 불안정성:** 운영진이 줄바꿈이나 띄어쓰기 규칙을 조금만 어겨도 정규식 파서가 붕괴되는 예외 상황.
2. **실시간 상태 동기화의 정합성:** 게임 서버(Minecraft)와 디스코드 음성 채널 상태를 Redis Pub/Sub 및 Tailscale VPN으로 묶을 때 발생하는 패킷 유실과 지연.

다음 **Part 2**에서는 이러한 복병들을 코드 레벨에서 어떻게 트러블슈팅하고 견고한 아키텍처로 리팩터링했는지를 다룬다.
