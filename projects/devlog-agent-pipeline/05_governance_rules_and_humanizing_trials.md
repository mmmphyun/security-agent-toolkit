# DevLog 파이프라인 엔지니어링: AI의 글쓰기 왜곡과 3중 거버넌스 방어

## 1. 개요 및 문제의식

DevLog 자율 에이전트 파이프라인을 구축하고 실제 강의 실습 및 자율 프로젝트를 블로그 포스트로 변환하는 과정에서, 단순한 텍스트 생성 이상의 미묘하고 치명적인 AI 글쓰기 왜곡 현상들이 관측되었다.

프롬프트에 단순한 지침만 부여했을 때 발생하는 한계와, 이를 해결하기 위해 `AGENTS.md` 거버넌스 개정 및 `pipeline/harness.py` 린터 하드웨어 방어선으로 승화시킨 기술적 시행착오를 기록한다.

## 2. 발생했던 9대 시행착오와 원인 분석

### 2.1. 화자 시점의 왜곡 (3인칭 대상화 문제)
- **현상:**
  블로그 본문에서 글쓴이 본인을 `"개발자가 2~3주간 직접 관리자 실무를 수행했다"`, `"개발자는 원인 조사를 위해 매번 SSH로 접속해 수동 디버깅에 의존했다"`와 같이 제3자 관찰자 시점으로 대상화하여 호칭하는 현상 발생.
- **원인 분석:**
  `AGENTS.md`의 `"시니어 엔지니어의 객관적 테크니컬 라이팅 어조 유지"`라는 지침을 LLM이 기계적으로 해석하여, 블로그의 원래 주인(1인칭 필자)을 외부에서 취재하고 평가하는 제3자로 인식함.
- **해결책 및 문체 규칙 확립:**
  - 작성자를 '개발자', '작성자'로 지칭하는 제3자 대상화 표현 전면 금지.
  - 불필요한 주어("나는", "필자는", "개발자는")를 내세우지 않고, **능동적 기술 의사결정과 엔지니어링 행동 중심의 담백한 평어체(`~했다`, `~를 적용했다`, `~를 구축했다`)로 서술**.

### 2.2. '코드 블록 필수' 템플릿 강박과 가상 코드 창작 (Hallucination)
- **현상:**
  인프라 구성, 사설 메쉬 VPN 보안, 도그푸딩 협업 중심의 회고글(실제 레포에 해당 코드가 없거나 마인크래프트 플러그인 등 다른 환경인 경우)에서, LLM이 존재하지 않는 가상 경로(`src/bot/cogs/sync.py`, `src/bot/cogs/whitelist.py`)와 가상 파이썬 함수를 임의로 지어내어 코드 블록에 삽입함.
- **원인 분석:**
  ADR 템플릿에 "코드 스니펫 대조"가 의무 항목처럼 규정되어 있어, LLM이 '코드를 넣지 않으면 템플릿 미준수로 실패'한다고 판단하여 억지 의사 코드(Pseudo Code)를 창작함.
- **해결책 및 린터 방어:**
  - 코드 블록에 들어가는 모든 코드는 인제스트된 실제 파일에서 확인된 원본만 허용.
  - 소스코드가 없는 인프라·설계·협업 중심의 글은 억지 코드를 배제하고 Mermaid 시퀀스/흐름 다이어그램과 텍스트 아키텍처 분석으로만 완결.
  - `pipeline/harness.py`에 `check_code_paths` 린터를 구현하여, 마크다운 내 표기된 파일 경로가 실제 레포지토리에 존재하는지 검증하고 부재 시 하드 에러(Exit 1)로 차단.

### 2.3. 소제목 파편화와 가상 로드맵 창작
- **현상:**
  소제목(`### 4.1`, `### 4.2`, `### 4.3` 등)이 자잘하게 쪼개지며 글의 호흡이 부산스러워지고, 실제 소스코드 주석에 없는 가상 인프라(Redis, Celery, SOAR 등)를 마치 향후 로드맵인 것처럼 지어냄.
- **원인 분석:**
  기계적인 넘버링 템플릿과 AI의 과장성(Elaboration) 경향으로 인한 환각.
- **해결책:**
  - 소제목(`###`)은 2~3개의 굵직한 핵심 엔지니어링 단위로 통합.
  - 코드/주석에 근거 없는 가상 로드맵 창작을 전면 금지하고, 실제 구현 과정에서 느낀 모듈화 체감, 시간 제약 속 엣지 케이스 등 현실적 교훈 서술.

### 2.4. 지속 누적 메모의 자동 포스팅 방지 (선언형 Draft 거버넌스)
- **현상:**
  지속적으로 시행착오를 누적 기록하기 위해 생성한 메모 파일이, 17:00 정기 스케줄의 미작성 타겟 스캐너(`--scan-pending`)에 걸려 미완성 상태에서 자동으로 블로그 포스트 초안으로 생성될 위험 발생.
- **원인 분석:**
  하네스 스캐너가 `projects/` 내의 모든 마크다운을 맹목적으로 블로그 타겟으로 수집함.
- **해결책:**
  - 임의의 폴더 격리 대신 Frontmatter에 `status: "draft"` (또는 `draft: true`) 선언형 메타데이터 도입.
  - `pipeline/harness.py`의 `scan_pending_targets`에서 `status: draft` 파일을 감지해 대기 목록에서 원천 배제. 추후 완결 시 `status` 변경만으로 즉시 파이프라인에 편입 가능.

### 2.5. 5단 ADR 목차 획일화와 과목/성격별 전개 방식 딜레마
- **현상:**
  코드 로직 diff보다 주석의 심층 Q&A 리서치와 계층 아키텍처 설계가 핵심인 일차(예: Day 08)에서, 고정된 5단 ADR 템플릿(1차 코드 vs 결함 vs 리팩터링 코드 3단 대조)과 소제목 2~3개 통합 제한 규칙으로 인해 주석의 핵심 설계 논의가 지엽적인 코드 스켈레톤 설명 하위로 압축·흡수되는 현상 발생.
- **원인 분석:**
  - AI의 탈선과 가상 로드맵 창작을 막기 위해 5단 구조와 소제목 개수를 엄격히 틀어막았으나, 이것이 역으로 과목과 실습 성격(코드 구현 중심 vs 아키텍처/설계 중심)에 유연하게 대응하지 못하는 과도한 제약(Over-constraint)으로 작용함.
  - 그렇다고 소제목을 전면 자율화하면 2~3줄마다 마이크로 소제목이 난립하는 파편화(Subheading Soup)와 주석 키워드 기반의 외부 이론 환각이 발생함.
- **해결책 (4대 전개 유형 분류 및 근거 기반 가드레일):**
  - **과목/주제별 4대 전개 유형 분류:** 코드 구현/리팩터링형, 아키텍처/설계형, 인프라/환경 구축형, 보안 분석/위협 모델링형으로 지면의 무게중심을 다변화.
  - **소제목 근거 기반 가드레일(Grounding-based Guardrail):** 단순 개수 틀어막기 대신 '소스코드 함수/클래스 또는 주석 Q&A 블록과의 1:1 매핑', '소제목당 최소 2문단 이상의 서술 밀도', '최대 4~5개 상한'이라는 실체적 검증 규칙으로 전환.

### 2.6. 시각화 강박(Mermaid 필수)과 데이터 구조화 표(Table) 다변화
- **현상:**
  단순한 텍스트 파서나 정규식 실습(Day 01~03)처럼 단일 스크립트 실행 구조인 경우에도, `pipeline/harness.py`의 `check_mermaid` 린터가 Mermaid 블록 부재 시 하드 에러(Exit 1)를 발생시켜 억지로 2~3개짜리 무의미한 흐름 박스(`A -> B -> C`)를 그리는 시각적 강박 발생.
- **원인 분석:**
  글의 구조적 앵커(Visual Anchor)를 확보하려는 의도였으나, 'Mermaid 블록 존재'만을 맹목적으로 검사하여 단순 데이터 변환 포스트에서 불필요한 시각 피로도를 유발함. 그렇다고 시각화를 전면 해제하면 Wall of Text와 AI 줄글 나열로 퇴행함.
- **해결책 (시각화 규격 다변화 린터):**
  - 복합 시스템/보안 아키텍처는 Mermaid Flowchart/Sequence 유지.
  - 단순 데이터 변환/단위 모듈은 원본(Raw) → 정제(Clean) → 집계(Aggregated) 스키마 변화를 보여주는 **구조화된 마크다운 표(Markdown Table) 또는 ASCII I/O 맵**을 정식 시각화 요소로 인정.
  - `harness.py` 검증기를 `Mermaid OR 구조화 표(| ... |) 중 최소 1개 필수`로 유연화하여 줄글화를 방어하면서 과도한 Mermaid 강박 해소.

### 2.7. 과목 전환 시 코드 의존 가드레일 붕괴와 실체적 원천(Grounding Triad) 승격
- **현상:**
  1과목(파이썬/에이전트)에서 2과목(네트워크·ZT)으로 넘어가면서 파이썬 소스코드 분량이 20~30줄 수준으로 급감하고 Wireshark 패킷 관찰/시스템 명령어 실습 중심의 이론 수업으로 전환됨. 기존 가드레일이 "파이썬 소스코드의 함수/클래스 매핑"에만 묶여 있어, 패킷 분석이나 프로토콜 헤더 등 실제 실습의 핵심 내용을 소제목으로 다루지 못하거나 가상 함수를 지어낼 위험에 직면함.
- **원인 분석:**
  가드레일의 추상화 레벨이 '파이썬 함수/클래스'라는 특정 언어/구현체에 과적합(Overfitting)되어 있었음. 가드레일의 본질은 "함수 강제"가 아니라 "실제 해보지도 않은 이론 환각(Hallucination) 방어"에 있음.
- **해결책 (3대 실체적 원천으로 가드레일 승격):**
  - 과목마다 땜질식 예외를 추가하는 방식을 전면 배제하고, 소제목(`###`) 매핑 기준을 **'당일 인제스트된 3대 실체적 원천(Grounding Triad)'**으로 추상화 승격:
    1. **로컬 산출물:** 소스코드(함수/클래스/변수), 설정 파일(JSON/YAML), 분석 보고서/메모(`.md`), 패킷/로그 데이터.
    2. **커리큘럼 실습 명세:** 당일 노션에서 인제스트된 구체적 실행 명령어(`ping`, `netstat`), 프로토콜, 패킷 관찰 요구사항.
    3. **주석 및 트러블슈팅 기록:** 코드 인라인 주석, 에러 로그, 질의응답 리서치.
  - 3번 섹션(한계점/도전과제) 역시 단순 코드 결함뿐 아니라 상위 애플리케이션 로그의 한계, 비암호화 통신의 도청 취약점 등 시스템 환경이 내포한 보안 공격 표면까지 포괄하도록 일반화.

### 2.8. 인라인 주석의 소유권·성격 구분과 '주제 연관성(Relevance) 필터'
- **현상:**
  코드 파일 내에 강사가 미리 적어둔 기초 설명(`#`), 비활성화 코드, 데이터용 멀티라인 문자열, 작성자의 자체 리서치 메모가 혼재되어, AI가 강사의 튜토리얼 주석을 작성자의 생각으로 오인하거나, 주제와 무관한 잡담성 메모까지 본문에 억지 인용할 위험 발생.
- **원인 분석:**
  파이썬 문법상 `'''`와 `"""`가 모두 문자열/독스트링으로 취급되며, 주석 인용 규칙에 "최우선 반영" 같은 절대적 명령어를 부여하면 맹목적 인용으로 글의 응집도가 파괴됨.
- **해결책 (문법·위치·역할의 3중 분리 및 연관성 필터):**
  - **홑따옴표 3중 (`''' ... '''`):** 작성자 고유 리서치 및 현장 회고로 한정.
    - 객관적 기술 스펙/Q&A는 당일 주제와 직결되는 내용에 한하여 4번(엔지니어링 의사결정) 근거로 선별 인용.
    - 수업 성격/난이도 체감 등 상황 메모는 4번 소제목으로 쓰지 않고 5번(회고)의 현실적 맥락으로만 1문장 내외 자연스럽게 반영.
  - **쌍따옴표 3중 (`""" ... """`):** 변수에 대입된 데이터 문자열(str) 리터럴 및 표준 함수 독스트링으로 엄격 격리.
  - **한 줄 `#` 주석:** 강의 예제 사전 설명 및 비활성화 코드로 식별하여 왜곡 인용 원천 차단.

### 2.9. PR 머지 후 과거 브랜치 오염과 사전 브랜치 격리 의무화 (Pre-work Branch Isolation)
- **현상:**
  GitHub에서 PR이 머지 완료되어 닫힌 과거 브랜치(`docs/visual-harness-refinement`)에 체크아웃된 상태에서, 에이전트가 다음 작업 시작 시 브랜치 점검 없이 바로 파일 수정을 시작하여 작업 트리가 오염되고 브랜치 충돌 위험 발생.
- **원인 분석:**
  `AGENTS.md`에 "1작업 1브랜치"라는 선언적 원칙만 있고, "파일 수정 도구 호출 전 브랜치 상태 점검 및 최신 `origin/main` 신규 분기"라는 실행 선행 절차(Pre-condition)가 강제되어 있지 않아 에이전트가 쓰기 도구부터 호출하는 관성이 작용함.
- **해결책 (작업 착수 전 브랜치 격리 의무 명문화):**
  - 단순 조회가 아닌 파일 수정·작성을 동반하는 모든 엔지니어링 작업 착수 직전, 에이전트는 반드시 `git status` 및 `git branch -vv` 점검을 수행.
  - 현재 브랜치가 `main`이거나 머지 완료된 과거 브랜치일 경우, **파일을 수정하기 전에** 최신 `origin/main`에서 신규 작업 브랜치를 분기(`git fetch origin` 후 `git switch -c <branch> origin/main`)한 뒤 작업을 시작하도록 선행 절차를 강제.

### 2.10. 가독성 저하와 타이포그래피의 시각적 쉼표 부재
- **현상:**
  벨로그 등 상용 테크 블로그에 비해 텍스트가 빽빽하고 답답해 보이며 가독성이 현저히 떨어짐. 특히 윈도우 환경 기본 맑은 고딕의 굵고 뭉툭한 렌더링으로 인해 볼드(`**`), 인라인 코드(`` ` ``) 강조가 지면을 더욱 무겁게 만듦.
- **원인 분석:**
  - 본문 폰트 패밀리가 시스템 기본 고딕으로 폴백되어 렌더링 선명도와 가독성이 저하됨.
  - 마크다운 문법 중 인용구(`>`)가 전혀 활용되지 않아, 긴 줄글 사이에서 핵심 설계 원칙이나 결론을 시각적으로 환기해 주는 '시각적 쉼표'가 부재함.
- **해결책 (Pretendard 웹폰트 및 인용구 카드 스타일링):**
  - Astro 블로그 헤더에 Pretendard v1.3.9 웹폰트 CDN을 연결하고, 본문 폰트 최우선 선언. 자간(`-0.012em`)과 행간(`1.8`)을 미세 조정하여 얇고 정갈한 서체 리듬감 확보.
  - `blockquote` 요소에 세련된 카드 스타일(좌측 4px 포인트 보더, 은은한 배경색, 패딩)을 부여하여 섹션별 핵심 요약 및 아키텍처 원칙을 인용구 카드로 조판하도록 거버넌스 개정.

### 2.11. 과목 카테고리 매핑 누락과 하네스 SSOT 부재
- **현상:**
  2과목(네트워크·Zero Trust) Day 01 포스트가 생성될 때 Frontmatter `category`가 1과목 명칭인 `"보안 자동화"`로 오분류되어 배포됨.
- **원인 분석:**
  - 커리큘럼 허브 노션 문서에 명시된 강의 분류명과 블로그 아카이브 상단 탭 필터링 기준이 1:1로 결합되어 있지 않았음.
  - 에이전트 프롬프트에 구체적인 매핑 테이블이 없어 기존 1과목 포스트의 Frontmatter 카테고리를 관성적으로 복사함.
  - 하네스 검증기에 슬러그 접두사(`c01~c05`)와 Frontmatter `category`의 일치 여부를 검증하는 로직이 부재했음.
- **해결책 (1~5과목 전체 카테고리 매트릭스 선제 명문화 및 결정론적 검증기):**
  - `AGENTS.md`에 1과목부터 5과목, 자율 프로젝트까지 디렉토리, 슬러그 접두사, Frontmatter 카테고리 규격, 블로그 탭을 명시한 SSOT 테이블 확립.
  - `pipeline/harness.py`에 `check_category_mapping` 검증기를 추가하여 슬러그 접두사와 카테고리 불일치 시 하드 에러(Exit 1)로 차단.
  - 블로그 상단 탭(`BlogArchive.astro`)에 3~5과목 탭을 선제적으로 추가하여 과목 전환 시 프론트엔드 수정 없이 자동 필터링되도록 구축.

### 2.12. AI 텍스트 벽(Wall of Text)과 요약 없는 2~3문장 분절 강제 린터
- **현상:**
  LLM이 생성한 본문 단락이 5~8문장(300~500자) 이상 줄바꿈 없이 길게 이어지며 독자에게 텍스트 벽(Wall of Text) 피로감을 유발함.
- **원인 분석:**
  - LLM의 자연스러운 생성 호흡은 문맥이 완전히 전환될 때까지 한 문단으로 묶으려는 경향이 강함.
  - 이를 막기 위해 "문단을 짧게 쓰라"거나 "요약하라"는 지침을 주면 기술적 깊이와 인과관계가 파괴되고, 단순 불릿 리스트로 퇴행하여 가독성이 더 악화됨.
- **해결책 (내용 축약 없는 2~3문장 엔터 분절 린터):**
  - 기술적 내용을 축약·삭제하지 않고, 오직 문맥의 결에 따라 2~3문장 단위로 줄바꿈(`\n\n`)만 삽입하여 시각적 여백을 확보하도록 조판 원칙 수립.
  - `pipeline/harness.py`에 문단 호흡 린터(`check_paragraph_pacing`)를 구현. 4문장 이상이면서 250자 이상이거나 350자를 초과하는 문단 감지 시 하드 에러와 함께 "내용을 삭제하지 말고 2~3문장 단위로 줄바꿈만 수행하라"는 자가 교정 지침을 명시적으로 피드백.

### 2.13. 획일적 헤더 강제의 경직성과 주 산출물(Hero Artifact) 위계 거버넌스
- **현상:**
  - `## 3. 기존 체계의 한계와 도전 과제`로 토씨 하나 틀림없이 기계적 고정을 강제하자, 모든 글의 목차가 동일한 붕어빵 헤더로 도배되어 글의 구체적인 기술 정체성이 은폐됨.
  - 에이전트가 고정된 H2 아래에서 기술적 맥락을 드러내기 위해 `### 3.1. ...`, `### 3.2. ...` 등 1문단짜리 마이크로 소제목(Subheading Soup)을 과도하게 생성하여 파편화된 결함 나열로 퇴행함.
  - 또한, 과목 실습을 획일적으로 '1차 코드 vs 리팩터링 코드 diff'로 규정하거나 파일 확장자 기반으로 단순 결정론을 적용할 경우, 네트워크(`network_zt`) 과목처럼 **본질이 패킷 트레이서 토폴로지와 프로토콜 분석 보고서임에도 불구하고, 트래픽 발생용 20줄짜리 보조 파이썬 스크립트에 80%의 지면을 낭비하고 본질적 네트워크 분석이 밀려나는 심각한 주객전도(퀄리티 저하)** 발생.
  - 프로젝트 포스트 작성 과정에서 주민등록번호/신분증 등 민감한 컴플라이언스 표현 노출 우려, 1,200ms 같은 출처 불분명한 환각 수치 인용, 32자리 비정규화 문자열 변환 같은 단순 전처리를 핵심 엔지니어링 성과로 과대포장하는 등 사실성과 실무적 고민 사이의 균형 붕괴 관측.
- **원인 분석:**
  - **하네스와 프롬프트의 결속 불균형:** 파이썬 린터(`pipeline/harness.py`)의 `REQUIRED_SECTIONS`는 이미 키워드 매칭(`["한계", "기본 구현", "도전 과제", ...]`)으로 유연하게 설계되어 있었음에도, 프롬프트에서 불필요하게 완전 일치를 강제하여 발생한 과도한 경직성이었음.
  - **포맷 이원화의 함정과 파일 중심 판정의 한계:** 과목 글과 프로젝트 글을 별도 포맷으로 분리하는 것은 린터와 에이전트 복잡도를 폭증시키는 오버엔지니어링이며, 단순히 "파이썬 파일이 있는가?"라는 이진 판정은 하이브리드(코드 + 분석 보고서) 실습에서 도메인 본질을 왜곡함.
  - **컴플라이언스 키워드와 자랑의 왜곡:** 민감한 개인정보 처리 프로세스는 추상화된 보안 자격 심사로 승화되어야 하며, 단순 정규화가 아닌 '경계 검증 및 DB UNIQUE 제약조건을 통한 계정 탈취 차단'이라는 시스템 보안 본질로 서술되어야 함.
- **해결책 (표준 앵커 복합형 패턴 및 주 산출물(Hero Artifact) 위계 거버넌스):**
  - **3섹션 "표준 앵커 + 맥락 부제" 복합형 허용 및 산문 압축:**
    - `## 3. 기존 체계의 한계와 도전 과제: [당일 구체적 기술 병목]` 형태를 공식 허용하여 하네스 린터와의 호환성을 유지하면서도 목차의 구체성을 확보.
    - 섹션 3 내부 마이크로 소제목 생성을 금지하고 2~3문단 안팎의 단단한 산문으로 문제 상황을 압축 서술하도록 통제.
  - **주 산출물(Hero Artifact) 교차 판정 및 지면 무게중심 배정:**
    - 커리큘럼 명세(`--fetch-curriculum`)의 행동 목표(패킷 분석 vs 에이전트 구현) + 과목 도메인(`course_id`) + 파이썬 파일의 역할(보조 도구 vs 비즈니스 로직)을 3단계로 교차 대조하여 당일의 '주 산출물(Hero)'을 확정.
    - **소프트웨어 도메인:** 1차 코드 vs 리팩터링 diff 중심 서술.
    - **네트워크/분석 도메인:** 패킷, 헤더 비트 제약(RFC), 시스템 명령어, 토폴로지 분석을 주연으로 서술. 파이썬 코드는 패킷 발생을 위한 '보조 실행 도구(Supporting)'로만 간략히 다루며, 코드 diff로 주객전도되는 것을 엄격히 금지. 가상 파이썬 코드 생성을 원천 차단.
    - **자율 프로젝트 도메인:** 분산 토폴로지, 프로덕션 제약, 실무 트레이드오프 중심 서술.
  - **하네스 하드코딩 지양 및 프롬프트 거버넌스 통제:**
    - 키워드 블랙리스트를 파이썬 코드에 섣불리 추가하면 정당한 보안 기술 용어가 오탐(False Positive)될 수 있으므로, 하네스 파이썬 코드를 건드리지 않고 프롬프트 및 휴먼 인터뷰 기반 사실관계 검증으로 정밀 통제.

### 2.14. 프로젝트 카테고리 파편화와 하네스 프리픽스 검증의 사각지대
- **현상:**
  - `proj-rpg-sync-project-04` 포스트가 배포될 때, 기존 1~3편이 등록된 `"프로젝트/실시간 RPG 동기화 엔진"`이 아닌 `"프로젝트/RPG Sync"`라는 별개의 카테고리로 Frontmatter가 기재되어 블로그 카테고리 트리와 탭이 파편화되는 현상 발생.
- **원인 분석:**
  - **하네스 린터의 느슨한 프리픽스 검증:** `pipeline/harness.py`의 `check_category_mapping`에서 과목 포스트(`c01~c05`)는 `COURSE_CATEGORY_MAP`을 통해 정확한 명칭과 1:1 완전 일치를 검증했으나, 프로젝트 포스트(`proj-`)는 `if not actual_category.startswith("프로젝트/"):`로만 검사함. 즉, 접두사가 "프로젝트/"이기만 하면 뒤에 임의의 명칭(`RPG Sync`)이 와도 하네스를 통과하는 검증 사각지대가 존재했음.
  - **프로젝트 카테고리 SSOT 부재 및 프롬프트 주입 결함:** `AGENTS.md`의 카테고리 매핑 테이블에 프로젝트별 구체적 공식 카테고리 명칭(SSOT)이 명시되어 있지 않았고, 메인 에이전트가 서브에이전트를 호출할 때 이전 포스트를 확인하지 않고 임의의 영문 명칭(`category: "프로젝트/RPG Sync"`)을 프롬프트로 주입함.
- **해결책 (프로젝트 카테고리 SSOT 매핑 테이블 및 하네스 완전 일치 검증기 구축):**
  - `AGENTS.md` 및 `pipeline/harness.py`에 `PROJECT_CATEGORY_MAP`을 명시하여 슬러그 접두사(`proj-rpg-sync-project`, `proj-devlog-agent-pipeline`)와 표준 한글 카테고리(`"프로젝트/실시간 RPG 동기화 엔진"`, `"프로젝트/DevLog 자율 에이전트"`)를 1:1로 결합.
  - 하네스에서 등록된 프로젝트 슬러그는 지정된 공식 카테고리와 완전히 일치하지 않을 경우 즉시 하드 에러(Exit 1)로 차단하도록 검증 로직 강화.
  - 오분류된 `proj-rpg-sync-project-04` 포스트의 Frontmatter 카테고리를 `"프로젝트/실시간 RPG 동기화 엔진"`으로 즉시 복구.

## 4. 향후 아티클 승화 포인트

1. **"프롬프트 지시만으로는 LLM의 템플릿 강박(가상 코드 생성)을 막을 수 없다"**:
   - AI 에이전트의 환각을 통제하기 위해서는 프롬프트 가이드뿐만 아니라, 빌드 파이프라인에서 파일 시스템과 대조하는 **결정론적 린터(Deterministic Linter)**가 필수적이다.
2. **"테크니컬 라이팅에서 3인칭 객관성의 함정"**:
   - 객관적 어조를 요구할 때 AI가 작성자를 제3자로 소외시키는 현상을 방지하려면, '3인칭'이라는 표현 대신 '주어를 생략한 능동적 엔지니어링 서술'로 거버넌스를 정밀 정의해야 한다.
3. **"선언형 메타데이터를 통한 자율 에이전트의 작업 경계 제어"**:
   - 파일 위치를 복잡하게 분리하지 않고 Frontmatter의 `status: draft` 선언만으로 자율 에이전트의 작업 범위(Scope)를 안전하게 통제할 수 있다.
4. **"가드레일의 추상화: 함수 결속에서 실체적 원천(Grounding Triad)으로"**:
   - 특정 언어나 함수 단위에 묶인 가드레일은 과목이 바뀌는 순간 깨진다. '실제 인제스트된 3대 실체적 원천(로컬 산출물, 실습 명세, 주석)'으로 추상화 레벨을 끌어올려야 지속 가능한 자율 파이프라인이 완성된다.
5. **"인라인 주석의 시그널-노이즈 분리와 연관성 필터"**:
   - 코드 내 주석을 무차별적으로 인용하면 튜토리얼 찌꺼기나 잡담이 지면을 오염시킨다. 문법적 형태(`'''` vs `"""` vs `#`)와 위치에 따른 소유권 분리, 그리고 주제 연관성 필터가 동반되어야 순도 높은 ADR을 추출할 수 있다.
6. **"원칙 선언과 절차적 강제의 차이 (사전 브랜치 격리)"**:
   - '머지된 브랜치 재사용 금지'라는 규칙 선언만으로는 에이전트의 쓰기 도구 호출 관성을 막을 수 없다. '파일 수정 직전 상태 확인 및 분기 생성'이라는 선행 절차(Pre-condition)를 명시해야 깃 트리 오염을 원천 방지할 수 있다.
7. **"시각화의 목적은 '다이어그램 넣기'가 아니라 '구조적 앵커 제공'이다"**:
   - 모든 글에 Mermaid를 강제하는 린터는 단순 실습에서 무의미한 박스 나열을 유발한다. 데이터 변환 표나 I/O 인터페이스 맵 등 대체 구조화 요소를 허용해야 본질적인 가독성을 지킬 수 있다.
8. **"가독성은 문장 축약이 아니라 타이포그래피와 시각적 쉼표에서 나온다"**:
   - AI 줄글의 피로도는 내용을 깎아내거나 불릿 리스트로 도배한다고 해결되지 않는다. 깔끔한 서체(Pretendard), 인용구(`>`) 카드를 통한 핵심 원칙 강조, 그리고 2~3문장 단위의 물리적 엔터 분절 린터가 결합되어야 엔지니어링 깊이와 가독성을 동시에 만족할 수 있다.
9. **"카테고리 누락을 방어하는 SSOT 매트릭스와 하네스 계약"**:
   - 커리큘럼 전환기마다 발생하는 메타데이터 오분류는 에이전트의 기억에 의존할 것이 아니라, 디렉토리-슬러그-카테고리-상단탭을 잇는 단일 SSOT 매트릭스를 정의하고 린터가 이를 계약(Contract)으로 검증해야 한다.
10. **"포맷의 다형성과 주 산출물(Hero Artifact) 위계: 하이브리드 실습의 주객전도 방어"**:
    - 문서 유형마다 포맷을 쪼개는 것은 에이전트의 환각과 린터 복잡도를 가중시키며, 단순 파일 확장자 기반 판정은 하이브리드 실습에서 보조 코드 diff로 지면을 낭비하는 주객전도를 낳는다. 보편적 문제 해결 서사인 5단 ADR 뼈대 위에서 커리큘럼 목표와 도메인을 통해 '주 산출물(Hero)'을 판정하고 지면의 무게중심을 유연하게 배정하는 다형적 거버넌스가 기술적 진실성을 보장한다.
11. **"프리픽스 검증의 착시와 프로젝트 메타데이터 SSOT 완전 일치"**:
    - `startswith("프로젝트/")`와 같은 느슨한 접두사 검증은 하네스가 동작하고 있다는 착시를 줄 뿐, 실제로는 임의의 영문명이나 오분류를 방어하지 못한다. 프로젝트 슬러그별 기대 카테고리를 명시적 딕셔너리로 전수 바인딩해야 메타데이터 무결성을 결정론적으로 보장할 수 있다.
