*2교시. 방화벽 규칙 읽기 — 연결된 PC에 어디까지 허용할까*


### 점검문제

**1.** IP 주소·TCP 포트를 검사하는 것과 웹 요청의 경로·입력값을 검사하는 것은 무엇이 다른가? ‘서버의 443번 포트를 허용했다’는 결과가 어디까지 말해 주는지 설명해 보자.

- 정답과 해설
    
    주소·포트 검사는 어느 통신 상대와 서비스에 접속하는지 구분하고, 요청 내용 검사는 그 서비스에 어떤 동작과 값을 요청했는지 살핀다. 443번 허용은 해당 접속 조건을 통과했다는 뜻이며, 웹 요청 내용이 안전하다고 확인한 결과는 아니다.
    

**2.** 상태를 추적하는 방화벽은 패킷의 주소·포트 외에 무엇을 함께 확인하는가? 이 정보가 서버의 응답을 판단할 때 왜 필요한지 설명해 보자.

- 정답과 해설
    
    이미 허용한 연결의 기록과 진행 상태를 함께 확인한다. 이를 통해 도착한 패킷이 기존 연결에 대한 응답인지, 상대가 별도로 시작한 새 접속인지 구분한다. 서버 주소가 같다는 이유만으로 모든 패킷을 응답으로 허용하지 않는다.
    

**3.** NGFW와 WAF는 각각 어떤 검사에 초점을 두는가? 제품 이름에 해당 기능이 적혀 있으면 필요한 검사가 이미 적용된 것으로 보아도 될까?

- 정답과 해설
    
    NGFW는 주소·포트·상태 검사에 애플리케이션 식별이나 침입 방지 등을 결합하며, WAF는 웹 요청과 응답의 내용 검사에 초점을 둔다. 제품마다 기능이 다르고 겹칠 수도 있다. 기능의 존재와 실제 검사 정책의 적용 여부는 따로 확인해야 한다.
    

**4.** 같은 PC가 포털에 두 연결을 만들었다. A는 203.0.113.10:54001 → 192.168.20.100:443 / TCP, B는 203.0.113.10:54002 → 192.168.20.100:443 / TCP이다. 같은 서버의 같은 서비스이므로 하나의 연결로 기록해도 될까?

- 정답과 해설
    
    두 연결을 구분해야 한다. 출발지·목적지 IP, 목적지 포트, 전송 방식은 같지만 PC의 출발지 포트가 다르다. 방화벽은 양쪽 주소·포트와 전송 방식 등을 함께 사용해 통신을 구분한다.
    

**5.** 사내에서 종료한 서비스에 접속한 직원에게 오래 기다리게 하지 않고 실패를 알리려 한다. 지원하는 정책 중 DROP과 REJECT 가운데 어느 쪽이 이 목적에 맞을까? 서버로 요청이 전달되는지도 설명해 보자.

- 정답과 해설
    
    거부 응답을 보내는 REJECT가 목적에 맞는다. 요청은 서버로 전달하지 않고 실패를 알린다. DROP도 요청을 전달하지 않지만 별도 거부 응답이 없어 사용자가 재시도하다 시간 초과를 만날 수 있다.
    

**6.** 회사가 허용한 통신만 통과시키는 정책을 사용한다. 새 업무 프로그램의 접속이 DROP됐지만 공격이 발견된 것은 아니다. 공격이 아닌데도 차단될 수 있는 이유와 먼저 확인할 내용을 말해 보자.

- 정답과 해설
    
    새 프로그램에 필요한 목적지·서비스 허용 조건이 빠졌을 수 있다. DROP은 반드시 공격을 발견했다는 뜻이 아니다. 프로그램의 승인 여부와 실제 통신 정보, 일치한 규칙을 확인한 뒤 업무에 필요한 범위를 정해야 한다.
    

**7.** 14:10에 직원 PC 203.0.113.10에서 포털 접속이 시간 초과됐다. 발견한 차단 로그는 13:50의 203.0.113.20 → 같은 포털 접속이다. 이 로그로 직원의 14:10 접속이 방화벽에서 차단됐다고 결론 내려도 될까?

- 정답과 해설
    
    그럴 수 없다. 시각과 출발지 주소가 달라 별도 접속의 기록이다. 직원이 시도한 시각과 양쪽 주소·포트·전송 방식이 맞는 기록을 찾아야 한다. 시간 초과 화면만으로는 방화벽, 경로, 서버 중 어디에서 문제가 생겼는지 확정하기 어렵다.
    

**8.** 읽을 수 있는 HTTP 요청이 ‘GET /search?q=network HTTP/1.1’, ‘Host: portal.a-company.test’로 주어졌다. 요청 내용 검사 기능은 여기서 어떤 경로, 입력값, 웹사이트 이름을 살펴볼 수 있는가?

- 정답과 해설
    
    경로는 /search, 검색어 입력값은 network, 웹사이트 이름은 Host에 적힌 portal.a-company.test이다. 지원하는 검사 기능은 이 정보가 정한 형식이나 조건에 맞는지 살펴볼 수 있다. 목적지 IP와 포트만 비교하는 것보다 요청의 동작을 구체적으로 확인한다.
    

**9.** 검색어를 100자까지만 허용하는 검사 정책이 있다. 정상 직원이 150자를 입력해 차단됐다. 직원이 공격자라고 결론 내리거나 길이 제한을 모두 없애는 것이 적절할까?

- 정답과 해설
    
    둘 다 바로 결정할 수 없다. 확인된 사실은 입력값이 정한 길이 조건을 넘었다는 것이다. 정상 업무에 150자가 필요한지와 검사 기록을 확인하고, 업무 요구에 맞는 제한을 정해야 한다. 차단 결과 하나로 사용자의 의도를 확정하지 않는다.
    

**10.** 직원의 포털 접속을 출발지 203.0.113.10으로 허용해 두었다. 승인된 접속 방식이 바뀐 뒤 회사가 보는 출발지는 192.168.30.10이 됐다. 접속을 복구하려고 모든 출발지를 허용하는 것이 적절할까?

- 정답과 해설
    
    적절하지 않다. 직원은 같아도 규칙이 비교하는 주소가 달라진 상황이다. 승인된 접속 방식과 실제 출발지 주소를 확인하고 필요한 대상만 허용해야 한다. 모든 출발지를 허용하면 다른 PC의 접속까지 열릴 수 있다.
      

**11.** (추가 과제) 직원 PC 203.0.113.10이 사용하는 포털 192.168.20.100을 HTTP TCP 80에서 HTTPS TCP 443으로 바꾼다고 하자. 전환 중에는 두 서비스를 제공하고, 전환이 끝나면 HTTPS만 제공한다. 두 단계의 허용 범위를 설명해 보자.

- 해설 보기
    
    전환 중에는 같은 직원 PC와 포털 사이의 TCP 80·443이 필요한지 확인해 허용한다. 전환 후에는 TCP 443을 유지하고 필요가 없어진 TCP 80 허용을 제거한다. 편의를 위해 모든 서비스를 허용할 필요는 없다. 이 문제는 규칙 조건의 비교이며 서버 전환을 실행하는 절차가 아니다.
    

**12.** (추가 과제) 투명 방화벽은 통신을 넘길 때 같은 네트워크의 두 구간을 잇는 방식으로 동작한다. 이를 2계층 연결 방식이라고 부른다. 그렇다면 이 장비는 IP 주소나 TCP 포트를 검사할 수 없을까?

- 해설 보기
    
    검사할 수 있다. 통신을 어떤 방식으로 넘기는지와 어떤 정보를 검사하는지는 별개의 기준이다. 투명하게 연결하면서도 지원 기능에 따라 IP·포트 등의 규칙을 적용할 수 있다. 2계층이라고 회사 내부에만 설치해야 하는 것도 아니다. 기존 IP 구성을 크게 바꾸지 않고 검사 지점을 추가할 때 고려하지만, 장비에 따라 관리용 IP와 연결·허용 규칙 등의 설정이 필요하다. “IP가 전혀 없고 케이블만 끼우면 끝”이라는 뜻은 아니다. 여기서는 연결 방식의 차이를 이해하며, 장비를 추가하는 실습은 하지 않는다.
    

**13.** (추가 과제) VPN에 연결한 PC가 주소를 받았다. 다른 시간에 다른 PC가 같은 주소를 배정받을 수 있는 환경이라면, 기록에 남은 그 주소만 보고 특정 직원의 접속이라고 단정해도 될까?

- 해설 보기
    
    주소만으로 단정하지 않는다. 해당 시각에 그 주소가 어느 VPN 접속에 배정됐는지, 어떤 계정이 연결했는지를 함께 확인해야 한다. 주소는 통신 대상을 구분하고, 접속 기록은 그때 사용한 계정과 주소의 관계를 확인하는 데 쓰인다. 주소가 항상 특정 직원에게 고정되는 구성인지도 확인한다. 계정이 확인되어도 계정 도용 여부나 허용할 업무 범위까지 모두 증명되는 것은 아니다.



### rpg-sync 프로젝트에서 방화벽 세팅했던 경험

1. GCP VPC 방화벽 (오리진 서버 보호)
GCP 콘솔(VPC network > Firewall)에서 직접 생성했거나 건드렸을 규칙들입니다.

기본 정책: 기본 제공 규칙 중 불필요한 인바운드 차단 및 사용자 정의 허용 규칙 추가.

인바운드(Ingress) 규칙 세부:

HTTP/HTTPS (80, 443 포트)

소스 IP: 0.0.0.0/0이 아닌 Cloudflare IP 대역(CIDR 목록)만 등록.

목적: Cloudflare CDN/WAF를 우회하여 GCP 공인 IP로 직접 들어오는 웹 트래픽 차단.

SSH (22 포트)

소스 IP: 전체 개방을 막고 본인 집/작업실 IP, 혹은 Tailscale 도입 후 Tailscale 사설 IP 인터페이스 대역(100.64.0.0/10)만 허용.

Tailscale 통신용 UDP (기본 41641 포트)

소스 IP: 0.0.0.0/0 (WireGuard P2P 터널링 핸드셰이크를 위해 UDP 인바운드 허용).

Redis (6379 포트)

소스 IP: 공인 IP(0.0.0.0/0)는 완전 차단.

외부 마인크래프트 서버와 Tailscale로 묶인 경우, Tailscale 가상 사설 IP(100.x.y.z) 대역만 인바운드 허용.

아웃바운드(Egress) 규칙:

기본 규칙인 allow-all-egress(0.0.0.0/0:all) 유지 (Supabase 호출, R2 API 업로드, Discord API 통신이 이 기본 규칙으로 나감).

2. Supabase 방화벽 (데이터베이스 접근 제어)
Supabase 대시보드(Project Settings > Database > Network Restrictions)에서 설정한 내용입니다.

네트워크 제한(Network Restrictions / IP Allowlist):

모드: 기본 완전 개방 상태에서 제한(Enforce) 모드로 변경.

등록한 소스 CIDR: GCP VM의 고정 공인 IP(Static External IP, /32).

목적:

5432(PostgreSQL 직접 연결) 및 6543(PgBouncer 커넥션 풀러) 포트에 대해 GCP 서버 외의 접속 완전 차단.

DB 비밀번호가 유출되거나 GitHub에 노출되는 사고가 발생해도 외부 해커가 DB에 직접 붙지 못하도록 L4 네트워크 단에서 방어.

3. Cloudflare R2 및 에지 보안 (객체 스토리지 접근 통제)
R2는 전통적인 IP 기반 VPC 방화벽이 아닌, 버킷 정책(Bucket Access Policy)과 API 자격 증명, WAF 규칙으로 방화벽 역할을 수행합니다.

공개 접근 제어 (Public Bucket Setting):

R2 대시보드에서 Public Access 활성화 시 커스텀 도메인(assets.yourdomain.com)만 바인딩.

기본 제공되는 개발용 도메인(pub-xxxx.r2.dev)은 비활성화하거나 차단.

API 토큰 권한 범위(Scoping):

GCP의 FastAPI 백엔드가 R2로 이미지를 업로드할 때 사용한 토큰: Object Read & Write 권한만 부여하고 계정 전체 관리 권한(Admin) 배제.

Cloudflare WAF / Page Shield (L7 방화벽):

R2 커스텀 도메인 앞단에 Cloudflare WAF가 기본 적용되어, 비정상적인 대량 요청(DDoS)이나 스크래핑 봇 차단.

읽기(Read)는 전 세계 누구나 CDN을 통해 가능하지만, 쓰기(PUT/POST/DELETE)는 S3 서명 인증(AWS SigV4) 헤더가 없는 요청은 Cloudflare 에지 단에서 즉시 403으로 차단.
