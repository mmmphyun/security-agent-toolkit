## 실제 현업 대형 IT 기업의 아키텍처 구조가 궁금해. 도커 컨테이너는 몇 개가 어떤 역할로 존재하는지, 이를 오케스트레이션하는 쿠버네티스 파드는 어떻게 어떤 단위로 묶어서 구성하는지 등.

대형 IT 기업의 인프라는 정형화된 단일 수치가 아니라 서비스 도메인과 트래픽 패턴에 따라 수천에서 수만 개의 컨테이너가 유기적으로 배포되는 구조를 취합니다.

브리핑
### 1. 도커 컨테이너의 역할과 규모

규모: 엔터프라이즈 환경에서는 고정된 개수가 아닌 HPA(Horizontal Pod Autoscaler) 기반으로 동작하며, 클러스터당 적게는 수천 개에서 많게는 수만 개의 컨테이너가 실시간으로 프로비저닝됩니다.

주요 역할군:

API/Business App: 주문, 결제, 회원 등 도메인별 마이크로서비스(Spring Boot, Go, Node.js 등).

Sidecar: 로그 수집(Fluentbit/Vector), 분산 추적(OpenTelemetry), 서비스 메시 프록시(Envoy), 보안/인증 에이전트.

Event/Batch: Kafka/RabbitMQ 컨슈머, Spark/Flink 워커, 배치 크론잡.

In-Cluster Cache/Proxy: NGINX Ingress, API Gateway, Envoy. (단, DB나 고부하 레디스는 컨테이너가 아닌 관리형 클라우드 서비스나 전용 베어메탈 인스턴스로 분리하는 것이 일반적)

### 2. 쿠버네티스 파드(Pod) 묶음 단위 및 배치 원칙

1 파드 = 1 메인 프로세스 + 보조 프로세스(Sidecar):

비즈니스 로직을 처리하는 메인 컨테이너 1개와 인프라 보조 컨테이너(Envoy 프록시, 로그 전달기 등) 1~2개를 하나의 파드로 결합합니다.

서로 다른 비즈니스 로직(예: 회원 서비스와 결제 서비스)을 동일 파드에 묶지 않습니다. 라이프사이클과 스케일링 단위가 다르기 때문입니다.

배포 및 클러스터 격리 전략:

네임스페이스 단위 격리: 개발/스테이징/프로덕션 환경 구분 또는 결제(PCI-DSS 대응 필요 영역)/일반 서비스 등 규제 도메인별 논리적 분리.

노드 어피니티 및 테인트(Taint/Toleration): 고성능 CPU/GPU가 필요한 AI 서빙 파드, 메모리 집약적인 캐시 파드, 일반 웹 파드를 물리적 노드 풀 단위로 분리 배치.

안티 어피니티(PodAntiAffinity): 고가용성(HA)을 위해 동일 서비스의 파드들이 동일 노드나 동일 가용 영역(AZ)에 몰리지 않도록 분산 스케줄링.



## AWS 기반 대규모 B2B SaaS 환경, 사용자의 요청이 인터넷을 거쳐 데이터베이스에 도달할 때까지 거치는 트래픽의 흐름(L4/L7 -> Ingress -> Pod -> DB)을 기준


### 1. 전체 아키텍처 계층 및 컨테이너 역할
```
[인터넷 / 테넌트 요청]
        │
        ▼
[AWS Route 53 / CloudFront]  -> 테넌트 라우팅 및 CDN/WAF 방어
        │
        ▼
[AWS ALB (L7 로드밸런서)]     -> TLS 오프로딩, 서브도메인 기반 라우팅
        │
        ▼
[EKS 클러스터 내부]
 ├── Ingress-NGINX / Envoy Pod -> 클러스터 내부 관문
 │
 ├── [Core App Tier (Pod 단위 구성)]
 │    ├── API Gateway / Auth Pod (테넌트 식별, JWT 검증)
 │    ├── Tenant Core Pod (조직/권한 관리)
 │    └── Business Service Pod (결제, 데이터 처리 등)
 │
 └── [Sidecar Container] (각 Pod 내부에 함께 상주)
      ├── Envoy Proxy (Istio 서비스 메시 통신 암호화)
      └── Vector/Fluentbit (로그 스트리밍)
        │
        ▼
[데이터 및 비동기 파이프라인 (클러스터 외부 분리)]
 ├── Amazon Aurora PostgreSQL (테넌트 데이터 저장소)
 ├── Amazon ElastiCache Redis (세션 캐싱, 분산 락)
 └── Amazon MSK (Kafka) / SQS (비동기 이벤트 처리)
```
### 2. 파드(Pod) 구성 및 묶음 단위 원칙
대형 SaaS 환경에서 파드를 묶는 기준은 "배포 주기"와 "스케일 아웃 단위"입니다.

왜 여러 컨테이너를 하나의 파드에 넣지 않는가?

결제 API와 회원 API를 한 파드에 묶으면, 결제 트래픽만 폭증할 때 회원 서비스까지 불필요하게 스케일 아웃되어 리소스가 낭비됩니다. 또한 한쪽 버그로 파드가 다운되면 다른 서비스까지 함께 중단됩니다.

따라서 비즈니스 로직(메인 앱)은 파드당 1개만 둡니다.

그렇다면 파드 안의 '멀티 컨테이너'는 언제 쓰는가? (Sidecar 패턴)

메인 앱과 수명 주기를 같이해야 하지만 비즈니스 로직과 무관한 인프라 공통 작업일 때 사용합니다.

예시 (1개 파드 구성):

app-container: Spring Boot 또는 FastAPI 기반 결제 비즈니스 로직

envoy-sidecar: 다른 파드와의 mTLS 암호화 통신 및 트래픽 메트릭 수집

log-sidecar: 앱이 파일로 떨군 로그를 수집해 중앙 모니터링 시스템으로 전송

### 3. B2B SaaS 환경만의 핵심 특성: 테넌트 격리(Multi-tenancy)
B2B SaaS는 기업(테넌트) 고객마다 데이터와 리소스가 엄격히 분리되어야 합니다. 실제 현업에서는 세 가지 방식을 혼용합니다.

컴퓨팅 격리 (네임스페이스/노드 풀 분리):

일반 테넌트는 공유 풀(Shared Node)의 파드에서 동시에 처리.

엔터프라이즈(VIP) 테넌트는 별도 EKS 네임스페이스 또는 전용 인스턴스(Node Affinity/Taint 활용)로 파드를 격리 배포.

데이터 격리 (Silo vs Pool):

고부하/보안 민감 고객: 전용 Aurora 인스턴스 할당(Silo).

일반 고객: 동일 DB 내에서 tenant_id 컬럼 또는 Schema 단위로 분리(Pool).


## 이것까지 봐도 감이 안오는데, 파드 당 하나의 컨테이너면 쿠버네티스를 쓰는 이유가 뭐야? 로드밸런서때문이야? 도커만으로 불가능해?


도커 자체는 **단일 서버 안에서 프로세스를 격리 실행하는 도구**일 뿐이며, 여러 대의 서버(수십~수백 대)로 인프라가 확장되는 순간 도커만으로는 운영이 불가능해집니다. 로드밸런싱은 쿠버네티스가 제공하는 수많은 기능 중 극히 일부입니다.

### 1. 단일 서버 도커 vs 멀티 노드 쿠버네티스

도커만 쓸 때와 쿠버네티스를 쓸 때의 차이를 장애와 운영 상황으로 비교하면 명확합니다.

| 상황 | 순수 도커 (Docker Engine) | 쿠버네티스 (K8s Orchestration) |
| --- | --- | --- |
| **서버 장애 (물리 서버 다운)** | 해당 서버에 있던 50개 컨테이너 전멸. 엔지니어가 새벽에 수동으로 다른 서버에 재기동 필요. | 컨트롤 플레인이 서버 사망을 감지하고, 살아있는 다른 노드에 파드를 즉시 자동 재배치(Self-Healing). |
| **트래픽 급증 (스케일 아웃)** | CPU/메모리 부하 시 엔지니어가 수동으로 `docker run` 명령어를 다른 인스턴스에서 실행하고 LB 설정 업데이트. | CPU 사용량 70% 초과 시 HPA가 파드 개수를 3개에서 50개로 자동 증설, 트래픽 분산까지 자동 처리. |
| **무중단 배포 (Rolling Update)** | 새 버전 배포 시 기존 컨테이너 중지 후 새 컨테이너 기동 사이에 다운타임 발생, 실패 시 롤백 복잡. | 새 버전 파드를 먼저 띄워 상태 검사(Readiness Probe) 통과 확인 후 트래픽을 넘기고 구버전 파드 순차 종료. |
| **서비스 검색 (Service Discovery)** | 컨테이너가 죽었다 살아나면 IP가 변경됨. 이를 바라보는 다른 서버들의 설정 파일을 일일이 갱신해야 함. | `CoreDNS`가 내장되어 있어 파드 IP가 바뀌어도 고정된 서비스 도메인(예: `order-service.default.svc`)으로 내부 통신 유지. |

### 2. "파드당 메인 컨테이너 1개"인데 왜 파드(Pod)라는 개념이 필요한가?

도커 컨테이너는 오직 단일 리눅스 격리 공간(cgroups, namespaces)입니다. 반면 쿠버네티스의 기본 실행 단위가 컨테이너가 아닌 '파드'인 이유는 다음과 같습니다.

* **네트워크 네임스페이스 공유**:
* 파드는 독립된 가상 IP를 1개 부여받습니다.
* 파드 안의 컨테이너들은 `localhost`로 통신하며 포트만 다르게 씁니다.


* **볼륨(디스크) 공유**:
* 파드 단위로 마운트된 임시 스토리지나 디스크를 내부 컨테이너들이 동시에 읽고 쓸 수 있습니다.


* **원자적 스케줄링(Atomic Scheduling)**:
* 비즈니스 로직(메인 앱)과 이를 감시하는 도구(로그 수집기, 보안 프록시)는 **반드시 물리적으로 같은 서버의 같은 메모리 공간**에 있어야 합니다.
* 쿠버네티스는 컨테이너를 따로 흩뿌리지 않고, 파드라는 껍데기 통째로 특정 노드에 묶어서 배치합니다.



---

### 3. 로드밸런서 때문인가?

반은 맞고 반은 다릅니다.

AWS ALB 같은 외부 로드밸런서는 클러스터 '문앞'까지만 트래픽을 전달합니다.
진짜 문제는 **클러스터 내부에서 벌어지는 초당 수만 건의 마이크로서비스 간 통신**입니다.

* A 서비스(결제)가 B 서비스(회원)를 호출할 때, B 서비스 파드 30개가 서로 다른 서버 10대에 흩어져 있습니다.
* 도커만 쓴다면 B 파드가 죽고 생길 때마다 A 서비스의 설정 파일에 B의 새 IP를 계속 적어줘야 합니다.
* 쿠버네티스는 `Service`와 `kube-proxy`를 통해 내부 가상 IP(ClusterIP)를 제공하고, 30개의 파드로 내부 트래픽을 알아서 L4/L7 단위로 균등 분산합니다.

---

요약하자면, 도커는 "프로세스 격리 포장재"이고, 쿠버네티스는 "수백 대의 서버를 마치 한 대의 거대한 컴퓨터처럼 다루며 자원 배치, 복구, 통신, 확장을 자동화하는 운영체제"입니다.


## 쿠버네티스는 좀 더 큰 단위네? 도커는 하나의 os 위에서 돈다고 치면, 쿠버네티스는 여러 서버에서 돌고, 여러 os를 품는거라고 보는거야? 아니면 각 서버의 os 위에서 도커처럼 돌긴 하는데, 각 서버의 k8s와 유기적으로 연결된거야?


후자(각 서버의 OS 위에서 돌면서 유기적으로 연결된 구조)가 기술적으로 정확한 설명입니다.

쿠버네티스가 여러 OS를 직접 품는 거대한 가상 머신(하이퍼바이저) 같은 것이 아닙니다. **물리적인 구조**와 **논리적인 관점**을 나누어 보면 이해가 명확해집니다.

---

### 1. 물리적인 실제 동작: "각 서버에 상주하는 에이전트들의 오케스트라"

각 서버(AWS라면 각각의 EC2 인스턴스)에는 리눅스 OS(Ubuntu, Amazon Linux 등)가 독립적으로 깔려 있고, 그 위에서 컨테이너 런타임(containerd)이 돕니다.

쿠버네티스는 이 서버들을 묶기 위해 지휘자(Control Plane)와 일꾼(Worker Node)으로 역할을 나눕니다.

```
[지휘 본부: Control Plane (Master Node)]
  ├── API Server: 모든 명령을 접수하는 창구
  ├── Scheduler: "새 파드를 어떤 서버에 띄울까?" 결정
  └── etcd: 클러스터의 모든 상태를 기록하는 DB
       │ (네트워크 통신)
 ┌─────┴─────────────────────────────────┐
 │                                       │
 ▼                                       ▼
[Worker Node 1 (EC2 #1)]                [Worker Node 2 (EC2 #2)]
 ├── Linux OS                            ├── Linux OS
 ├── kubelet (관리 에이전트)               ├── kubelet (관리 에이전트)
 ├── kube-proxy (네트워크 규칙 관리)       ├── kube-proxy (네트워크 규칙 관리)
 ├── containerd (실제 컨테이너 실행)      ├── containerd (실제 컨테이너 실행)
 └── [Pod A], [Pod B] 실행               └── [Pod C] 실행

```

* **`kubelet`**: 각 서버의 OS 위에서 백그라운드 프로세스(데몬)로 실행되는 에이전트입니다. 마스터의 지휘를 받아 "우리 서버에 파드 A 띄워라"라는 명령을 받으면 컨테이너를 실행하고, 상태를 마스터에 계속 보고합니다.
* **`kube-proxy` & CNI(네트워크 플러그인)**: Node 1의 Pod A와 Node 2의 Pod C가 마치 같은 스위치에 연결된 것처럼 서로의 고유 IP로 바로 통신할 수 있도록 OS 레벨의 라우팅/iptables 규칙을 실시간 동기화합니다.

---

### 2. 논리적인 관점: "엔지니어 눈에는 거대한 단일 컴퓨터"

인프라 엔지니어나 개발자 입장에서 쿠버네티스는 '수십 대의 분산 서버를 단 1대의 거대한 자원 풀(Pool)로 추상화한 가상 계층'입니다.

* 엔지니어는 "Node 3번 서버에 메모리가 남으니 거기에 컨테이너를 띄워야지"라고 명령하지 않습니다.
* "CPU 2코어, 메모리 4GB 필요한 파드 5개 띄워줘"라고 쿠버네티스 API Server에 선언문(YAML)을 던질 뿐입니다.
* 그러면 쿠버네티스가 알아서 서버 10대 중 자원이 넉넉한 곳을 찾아 흩뿌려 배포합니다.

---

### 요약

* **물리적 실체**: 각 서버의 개별 OS 위에 컨테이너 런타임과 쿠버네티스 통신 에이전트(`kubelet`)가 깔려서 마스터 서버와 유기적으로 통신하는 구조입니다.
* **논리적 결과**: 이 에이전트들이 네트워크와 자원을 하나로 묶어주기 때문에, 사용하는 사람 입장에서는 여러 대의 서버를 하나의 거대한 분산 OS처럼 다루게 됩니다.


## 정리

쿠버네티스의 물리적, 논리적 단위까지 알아보면서 완벽하진 않지만 큰 틀에서 이해를 완료했다.
도커 컴포스는 단일 호스트에서 컨테이너들을 묶는 역할을 하므로 보통 로컬 테스트 용도로 사용되고, 쿠버네티스는 대량의 서버에서 파드를 통해 컨테이너들을 관리하므로 프로덕션 환경에서 사용된다.
물론 나는 '단일 서버'에 봇, 웹, redis의 각각의 컨테이너를 묶어 배포하기 위해 rpg-sync에서 도커 컴포스로 운영했다.
