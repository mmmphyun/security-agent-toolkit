### 이전과 달리 www를 무조건 포함시키지 않아도 되는 이유가 os나 브라우저에서 편의기능을 제공하는건지, 무언가 규칙이 변경된건지?

www를 생략하는 현상은 DNS 프로토콜 표준이나 네트워크 규칙이 바뀐 것이 아닙니다. 기술 표준은 예전과 동일하지만, 브라우저의 주소창 처리 방식, DNS 레코드 최적화 기술, 그리고 웹 서버의 리다이렉트 표준화가 결합되어 관행이 변한 결과입니다.

기술적 본질: 규격은 변하지 않음

example.com은 Apex 도메인(Root/Naked Domain)입니다.

[www.example.com](https://www.example.com)은 호스트 이름이 www로 지정된 서브도메인(Subdomain)입니다.

과거 인터넷 초기에는 서비스 프로토콜별로 호스트명을 분리하는 것이 관례였습니다(www는 웹, ftp는 파일 전송, mail은 메일). 현재도 DNS 계층에서는 둘을 완전히 별개의 도메인 레코드로 취급합니다.

www가 사라진 기술적·환경적 요인

브라우저의 주소 파싱 및 UI 간소화:

주소창에 프로토콜(http://, https://)이나 www를 입력하지 않아도 브라우저가 기본값으로 처리하거나, 주소창 표기 시 시각적으로 숨기는 처리를 도입했습니다.

사용자가 example.com만 입력해도 브라우저는 해당 도메인으로 바로 HTTP 요청을 보냅니다.

웹 서버 및 CDN 계층의 표준 리다이렉트 (Canonicalization):

과거에는 두 주소의 설정을 따로 두는 경우가 많았으나, 검색 엔진 최적화(SEO)와 트래픽 단일화를 위해 한쪽 주소로 강제 301 영구 이동(Permanent Redirect)을 시키는 것이 웹 표준 아키텍처로 자리 잡았습니다.

브랜드 인지도와 간결함을 위해 example.com을 메인(Canonical)으로 잡고, www로 들어온 요청을 루트로 리다이렉트시키는 구성이 보편화되었습니다.

DNS 공급자들의 기술적 한계 극복 (CNAME Flattening / ALIAS):

본래 DNS 표준(RFC 1034)상 루트 도메인(example.com)에는 SOA, NS 레코드가 반드시 존재해야 하므로 CNAME 레코드를 설정할 수 없었습니다.

이 때문에 CDN이나 PaaS처럼 도메인 기반(CNAME) 연결이 필수적인 서비스를 루트 도메인에 연결하기 어려워 www를 서브도메인으로 사용해야만 했습니다.

그러나 Cloudflare의 CNAME Flattening, AWS Route 53의 Alias Record 등 DNS 공급자들이 루트 도메인에서도 내부적으로 CNAME을 A 레코드 IP로 치환해 응답하는 기능을 구현하면서 루트 도메인을 CDN에 직접 물리는 것이 기술적으로 가능해졌습니다.

전문가 관점의 주의점 및 평가

루트 도메인을 무조건 메인으로 쓰는 것이 항상 정답은 아닙니다. 대규모 엔터프라이즈 환경에서는 여전히 www를 권장하기도 합니다.

쿠키 스코프(Cookie Scope): 루트 도메인(example.com)에 발급된 쿠키는 설정에 따라 모든 하위 도메인(api.example.com, static.example.com)에 불필요하게 전송되어 보안 위험이나 네트워크 오버헤드를 유발할 수 있습니다. www를 쓰면 서브도메인 간 쿠키 격리가 용이합니다.

DNS 표준 호환성: CNAME Flattening을 지원하지 않는 자체 온프레미스 DNS나 폐쇄망 환경에서는 루트 도메인과 외부 CDN 연동 시 여전히 제약이 따릅니다.
