## 1. 개요 및 프로젝트 배경

이전 단계([proj-aleph-project-04-dynamodb-quorum-sliding-window](/posts/proj-aleph-project-04-dynamodb-quorum-sliding-window))에서 단일 키 기반 DynamoDB 슬라이딩 윈도우와 정족수 쿼럼($R + W > N$) 일관성 읽기를 설계하여, CloudWatch Logs 분할 배치 인입 시에도 상태를 보존하고 Stale Read 결함을 방어하는 상태 영속화 계층을 구축했다.

단일 키 낙관적 동시성 제어(OCC)를 적용한 상태에서 CI 멀티스레드 단위 테스트(`test_concurrent_record_failure_race_condition`)를 실행하자, 간헐적으로 `AssertionError: assert 4 == 5`가 터지는 동시성 레이스 컨디션 사고가 발생했다. 5개 스레드가 동일 파티션 키에 밀리초 단위로 동시 인입될 때 `ConditionExpression` 충돌로 재시도 루프가 소진되면서 1건의 업데이트가 유실된 것이다.

이 문제를 해결하기 위해 3대 엔지니어링 트레이드오프가 충돌했다. 10초 관통 SLA 예산 중 상태 영속화 계층에 허용된 시간은 수십 밀리초에 불과했다.

복수 Lambda 인스턴스가 밀리초 단위로 인입될 때 쓰기 무유실을 달성해야 했고, 5분 윈도우 경계면 및 비균등 버스트 트래픽 환경에서 오탐과 미탐을 0건으로 통제해야 했다.

클라우드 A 테크 리드로서 단순 지터 백오프 상향이라는 미봉책을 기각하고, 업계 표준으로 쓰이는 Cloudflare 식 가중 2-버킷 카운터를 포함한 4대 아키텍처 대안을 직접 구현하여 벤치마크를 수행했다. 대규모 트래픽과 달리 소규모 이산 임계치($N=5, 2$)를 다루는 침해사고 도메인에서 통계적 근사가 붕괴함을 수학적으로 실증하고, 시간 버킷 파티셔닝 기반 락 프리 `list_append`와 조회 시점 3-버킷 타임스탬프 슬라이딩 로그 구조로 전면 리팩터링을 단행했다.

## 2. 전체 산출물 구조 및 진단/파이프라인 체계

동시성 충돌 해결과 윈도우 정확도 확보를 위해 검토한 4대 아키텍처 대안의 수학적 모델, 동시성 메커니즘, 트레이드오프 비교는 다음과 같다.

| 아키텍처 대안 | 수학적/자료구조 모델 | 동시성 제어 메커니즘 | 탐지 정확도 한계 및 결함 | 채택 여부 |
|---|---|---|---|---|
| **대안 A<br/>(단일 키 OCC)** | 단일 파티션 키<br/>`BF#<ip>#<user>` | `ConditionExpression` 기반 CAS 재시도 루프 ($K=5$) | 정확도 우수하나, 고부하 동시 인입 시 재시도 소진으로 인한 **갱신 유실** 발생 | 폐기<br/>(CI 실패 원인) |
| **대안 B<br/>(고정 텀블링)** | 시간 버킷 파티션 키<br/>`epoch // 300` | DynamoDB 네이티브 `ADD` (조건식 없는 원자적 Upsert) | 윈도우 경계면 통과 시 카운트 분할로 5회 임계치 공격 **100% 탐지 누락** | 탈락<br/>(보안 사각지대) |
| **대안 C<br/>(가중 2-버킷)** | 시간 버킷 파티션 키 +<br/>선형 시간 감쇠 가중합 추정 | DynamoDB 네이티브 `ADD` (조건식 없는 원자적 Upsert) | 소규모 이산 공격($N=5$)에서 대수의 법칙 붕괴, **오탐 2건 및 미탐 2건** 발생 | 탈락<br/>(통계적 붕괴) |
| **대안 D<br/>(3-버킷 타임스탬프 로그)** | 시간 버킷 파티션 키 +<br/>타임스탬프 리스트 누적 | 조건식 없는 원자적 `list_append` (충돌률 0%, 1 RTT) | 조회 시점 직전/현재/직후 3-버킷 스캔 및 **양방향 닫힌 구간 $[ref-300, ref]$ 정밀 필터링 (정확도 100%)** | **최종 채택<br/>(PR #78 반영)** |

## 3. 기존 체계의 한계와 도전 과제: 단일 키 OCC의 재시도 소진과 CI 멀티스레드 레이스 컨디션

기존 4편에서 구축했던 단일 파티션 키(`BF#<ip>#<user>`) 기반 낙관적 동시성 제어(OCC)는 단일 Lambda 배치를 처리할 때는 정상 작동했다. 그러나 CI 환경에서 `ThreadPoolExecutor`를 활용해 5개 작업 스레드가 동일 키에 동시 인입되는 상황을 모사하자 `AssertionError: assert 4 == 5` 결함이 재현되었다.

단일 키 환경에서는 이전 윈도우의 만료 여부를 판별하기 위해 쓰기 시점에 조건식(`ConditionExpression="attribute_not_exists(target_key) OR expire_at >= :now"`)이 필수적이다. 동일 밀리초에 5개 스레드가 요청을 보내면 첫 번째 스레드만 CAS(Compare-And-Swap)에 성공하고 나머지 4개 스레드는 일제히 `ConditionalCheckFailedException`을 수신한다.

재시도 횟수를 늘리고 지터 백오프를 도입하는 방식은 10초 관통 SLA라는 제약과 정면으로 충돌했다. 10초 SLA 예산 중 DynamoDB 계층에 허용된 지연시간은 수십 밀리초에 불과했기 때문에, 백오프 대기 시간을 길게 잡으면 테일 레이턴시가 치솟아 SLA를 위반했다. 반대로 지터 간격을 5-25ms로 억제하면 복수 스레드가 지터 대기 후 다시 동일한 밀리초에 충돌하여 준비된 재시도 루프(최대 5회)를 순식간에 소진하고 최종 갱신 유실로 이어졌다.

CAS 루프에 의존하는 단일 키 OCC 방식은 동시 인입 빈도가 증가할수록 지연시간과 유실율이 가파르게 악화되는 구조적 한계를 안고 있었다.

## 4. 엔지니어링 의사결정 및 리팩터링

### 4.1. Cloudflare 가중 2-버킷 모델(선형 감쇠)의 이산적 붕괴 실측

단일 키 경합을 없애기 위해 시간 버킷 파티셔닝을 적용하되, 고정 텀블링 윈도우의 경계면 분할 결함을 극복하고자 Cloudflare가 제안한 가중 2-버킷 슬라이딩 윈도우 알고리즘 도입을 검토했다. 직전 버킷($B_{p}$)과 현재 버킷($B_{c}$)의 카운트를 읽어 현재 버킷의 경과 시간에 비례한 선형 감쇠 가중합을 계산하는 방식이다.

$$\text{Estimated Count} = \text{Count}(B_c) + \text{Count}(B_{p}) \times \left(1 - \frac{t_{\text{current}} \bmod 300}{300}\right)$$

이 알고리즘은 수천에서 수만 RPS가 지속적으로 유입되는 대규모 웹 트래픽 환경에서는 대수의 법칙에 의해 개별 트래픽의 불균등성이 상쇄되어 오차율이 0%에 수렴한다. 그러나 침해사고 대응 도메인은 **극단적 소규모 이산 임계치($N=5, 2$)**와 **비균등 버스트** 인입이라는 상반된 특성을 지닌다. 공격자는 5분 동안 균등하게 요청을 보내는 것이 아니라, 1초 동안 4회를 몰아치거나 단 수 초 내에 공격을 완결한다.

테스트 스위트로 계측한 결과, 직전 버킷 트래픽이 시간에 따라 균등하게 분포한다는 통계적 전제가 깨지면서 오차가 발생했다.

299초에 4건, 450초에 1건이 발생한 경우(151초 내 5회 집중 공격), 직전 버킷의 4건이 50%로 선형 감쇠되어 추정치가 $1 + 4 \times 0.5 = 3.0$으로 계산되어 탐지를 누락했다. 반대로 1초에 4건이 발생하고 302초에 1건이 발생한 경우(이벤트 간 간격 301초로 유효 윈도우 만료), 직전 버킷의 4건이 99.3%로 과대 반영되어 추정치가 $1 + 4 \times 0.993 = 4.97 \approx 5$로 계산되어 정상 트래픽을 차단하는 오탐이 발생했다.

대규모 웹 트래픽에서 검증된 통계적 근사 모델이라도, 이산적이고 비균등한 보안 도메인에서는 탐지 누락과 오차단을 유발하는 결함 모델임을 실측으로 규명했다.

### 4.2. 시간 버킷 파티셔닝 기반 락 프리 list_append 원자적 Upsert

통계적 근사를 버리고 실제 이벤트 발생 시각을 영속 보존하기 위해, 시간 버킷 파티셔닝과 타임스탬프 리스트 원자적 누적 구조(대안 D)를 설계했다.

파티션 키에 버킷 ID를 내포시킴으로써(`BF#<ip>#<user>#{epoch // 300}`), 이전 윈도우의 만료 여부를 판별하는 조건식을 완전히 제거했다. DynamoDB 스토리지 엔진은 조건식이 없는 요청에 대해 내부 메모리에서 직접 `ADD`와 `list_append`를 단일 트랜잭션으로 커밋한다.

```python
# src/remediation/auth_window.py
# 시간 버킷 파티셔닝 기반 락 프리 원자적 Upsert (조건식 없는 1 RTT 커밋)
new_timestamps = [now] * count
res_bf = self._table.update_item(
    Key={"target_key": bf_key},
    UpdateExpression=(
        "ADD failure_count :inc "
        "SET timestamps = list_append(if_not_exists(timestamps, :empty), :new_ts), "
        "expire_at = :exp, last_seen = :now"
    ),
    ExpressionAttributeValues={
        ":inc": count,
        ":new_ts": new_timestamps,
        ":empty": [],
        ":exp": expire_at,
        ":now": now,
    },
    ReturnValues="ALL_NEW",
)
```

이 설계의 핵심은 **쓰기 시점의 동시성 제어를 완전히 배제하고, 정확한 시간 윈도우 판정 책임을 조회 시점(`check_threat`)으로 분리**한 데 있다. 조건식이 없으므로 `ConditionalCheckFailedException` 경합이 물리적으로 0%가 되며, 5개 이상의 스레드가 동시 인입되더라도 단 1 RTT(10ms 내외) 만에 모든 이벤트가 누락 없이 영속 계층에 원자적으로 적재된다.

### 4.3. 분산 큐 순서 역전 극복과 양방향 닫힌 구간 3-버킷 필터링

쓰기 경로의 락을 제거한 대가로, 비동기 분산 수집 환경에서 발생하는 물리적 시간축 왜곡을 해결해야 했다. CloudWatch Logs 구독 필터는 분산 샤딩 스트림이므로, 복수의 Lambda Worker 컨테이너가 병렬 기동될 때 콜드 스타트 편차로 인해 $t=450$ 배치가 $t=299$ 배치보다 먼저 DynamoDB에 도달하는 시간축 역전이 발생했다.

단일 키 시절에는 덧셈 교환법칙($A+B=B+A$)이 성립했으나, 버킷 파티셔닝 환경에서는 버킷 ID 자체가 분할($t=450 \rightarrow$ 버킷 1, $t=299 \rightarrow$ 버킷 0)되므로 교환법칙이 붕괴했다. $t=299$를 뒤늦게 처리하는 Worker 관점에서 현재(0)와 직전(-1) 버킷만 조회하면 이미 커밋된 버킷 1을 놓치는 탐지 누락이 발생했다.

이를 해결하기 위해 직전(`curr - 1`), 현재(`curr`), 직후(`curr + 1`) 3개 버킷을 일괄 조회하여 지연 인입 시에도 선행 처리된 미래 버킷 데이터를 포괄하도록 설계했다. 이때 단순 하한선($t \ge now - 300$)만 둘 경우, $t=1$(3건) $\rightarrow$ $t=599$(1건) $\rightarrow$ $t=301$(1건) 순으로 역전 인입될 때 598초 차이나는 트래픽이 합산되는 오탐이 발생했다. 이에 따라 기준 시각 $ref$를 상한으로 강제하는 **양방향 닫힌 구간 $[ref - 300, ref]$ 정밀 필터링**을 구현했다.

```python
# src/remediation/auth_window.py
# 3-버킷 강한 일관성 읽기 및 양방향 닫힌 구간 [ref - 300, ref] 필터링
res_curr = self._table.get_item(Key={"target_key": bf_curr_key}, ConsistentRead=True)
res_prev = self._table.get_item(Key={"target_key": bf_prev_key}, ConsistentRead=True)
res_next = self._table.get_item(Key={"target_key": bf_next_key}, ConsistentRead=True)

all_ts = [int(t) for t in (item_curr.get("timestamps") or []) + 
                           (item_prev.get("timestamps") or []) + 
                           (item_next.get("timestamps") or [])]

# 기준 시각 후보군에 대해 [ref - 300, ref] 닫힌 구간 내 5회 도달 여부 정밀 평가
ref_candidates = set(all_ts) | {now}
for ref_time in ref_candidates:
    cutoff_low = ref_time - self.window_seconds
    cutoff_high = ref_time
    count_in_window = sum(1 for t in all_ts if cutoff_low <= t <= cutoff_high)
    if count_in_window >= BRUTE_FORCE_THRESHOLD:
        return True, "SSH_BRUTE_FORCE", bf_curr_key
```

### 4.4. 폐루프 차단 아키텍처와 TTL 기반 메모리 자연 수렴 특성

타임스탬프 리스트를 DynamoDB 아이템에 지속적으로 append하면, 대규모 DoS 공격 환경에서 단일 아이템 용량 한도(400KB)에 도달할 위험이 존재한다.

본 시스템은 탐지와 인프라 차단이 결합된 **폐루프 차단 아키텍처**로 이 문제를 운영적으로 해결했다. 5회 임계치에 도달하는 즉시 타깃 EC2의 L4 보안 그룹을 교체하여 후속 TCP SYN 패킷을 하이퍼바이저 레벨에서 드롭한다. 패킷이 타깃 OS 커널에 도달하지 않으므로 추가 로그 유입이 물리적으로 차단되어, 일반적인 공격 상황에서 단일 레코드의 리스트 길이는 5-10개 내외로 자연 수렴한다.

또한 각 시간 버킷 레코드에 10분 수명의 TTL(`expire_at = (bucket_id + 2) * window_seconds`)을 설정하여 만료된 버킷을 DynamoDB 백그라운드 엔진이 자동 소각하도록 조율했다. 인라인 소각을 위한 조건부 쓰기 경합을 유발하지 않고 스토리지 비대화를 원천 차단했다.

### 5.2. 현실적 회고 및 교훈

대규모 분산 환경에서 널리 찬사를 받는 알고리즘이라도 도메인의 물리적 특성이 다르면 치명적인 결함으로 변모한다. 초당 수만 건의 웹 트래픽 제어에 최적화된 가중 슬라이딩 윈도우 카운터는 대수의 법칙이 성립하지 않는 소규모 침해사고 대응 도메인($N=5$)에서 수학적 가정이 완전히 붕괴했다.

또한 분산 환경에서 동시성 충돌을 쓰기 시점의 락이나 조건식으로 통제하려 할 때 지연시간과 가용성이 급격히 훼손된다는 교훈을 얻었다. 시간 버킷 파티셔닝으로 쓰기 경로의 락을 완전히 해제하여 1 RTT 만에 데이터를 안전하게 적재하고, 슬라이딩 윈도우의 엄밀한 수학적 판별 책임을 조회 시점의 3-버킷 타임스탬프 필터링으로 분리함으로써 10초 관통 SLA와 100% 탐지 정밀도를 동시에 달성했다.
