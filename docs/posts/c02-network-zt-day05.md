## 1. 개요 및 학습 개념 요약

[이전 포스트](/security-agent-toolkit/blog/c02-network-zt-day04/)에서는 5-Tuple 확장형 접근 통제 목록과 방화벽 기반의 원격 접속 암호화 터널을 구축하고, 최소 권한 원칙을 강제하는 경계 보안 아키텍처를 실증했다. 사내 전산 자원에 대한 안전한 원격 접근 터널이 확보되더라도, 기업 인프라가 외부 서비스로 확장되는 순간 네트워크 경계는 근본적인 변화를 겪는다.

기업의 업무 환경이 온프레미스 전산실을 넘어 외부 클라우드 플랫폼으로 이전되면, 물리적 경계와 논리적 신뢰 경계가 일치하지 않는 현상이 발생한다. 외부 클라우드 서비스를 도입하더라도 인프라 운영의 책임이 완전히 사라지는 것은 아니며, 단일 통신 회선에 의존하는 토폴로지는 언제든 전사적 서비스 단절을 초래할 수 있다.

> 인프라를 외부 클라우드로 이전해도 데이터와 권한 관리의 책임은 이전되지 않으며, 안전한 서비스 운영은 엄격한 DMZ 분리와 회선 이중화에서 시작된다.

외부 클라우드 서비스와의 통신 경로를 확보하는 동시에, 사내 공개 서버를 안전하게 격리하고 외부 회선 단절에 대응하는 심층 방어 아키텍처를 검증했다. 분석 보고서와 시뮬레이션 토폴로지를 기반으로 클라우드 책임 경계, DMZ 세그멘테이션, 네트워크 품질 진단, 그리고 관리 거리를 활용한 부동 정적 라우트 이중화를 체계적으로 정립했다.

- **클라우드 책임 공유 모델과 서비스 형태별 경계:** 인프라 자원 제공 모델에 따른 관리 주체를 식별하고, 서비스 형태에 따라 기업에 남겨지는 고유한 운영 책임을 정의했다.
- **소유권 경계와 네트워크 경계의 분리:** 기업이 직접 관리하는 장비의 범위와 신뢰하는 네트워크 경계를 직교적으로 분리하여 관제 사각지대를 해소했다.
- **DMZ 세그멘테이션과 최소 권한 트래픽 통제:** 공개 웹 서비스를 내부 업무망과 분리된 방화벽 독립 인터페이스에 배치하고, 인바운드 허용과 횡적 이동 차단을 결합했다.
- **네트워크 품질 메트릭의 다계층 진단:** 회선 대역폭과 실제 처리량의 괴리를 규명하고, 왕복 시간 및 경로 추적 도구가 지닌 진단적 한계를 분석했다.
- **관리 거리 기반 부동 정적 라우트 이중화:** 주 회선과 예비 회선에 차등화된 관리 거리를 부여하여, 주 회선 장애 시 패킷 전달 경로를 무중단으로 우회시키는 장애 조치 체계를 실증했다.

## 3. 기존 체계의 한계와 도전 과제: 클라우드 책임의 착시와 단일 회선의 통신 병목

클라우드 컴퓨팅을 도입할 때 흔히 발생하는 치명적인 오판은 인프라와 소프트웨어의 모든 운영 책임이 서비스 제공자에게 일임된다는 착각이다. 물리 장비를 직접 구매하고 설치하는 공수는 절감되지만, 가상 서버 위의 애플리케이션 결함, 접근 권한 설정, 퇴사자 계정 통제는 온전히 기업의 관리 영역으로 남는다.

다중 인증을 거쳤더라도 특정 문서에 대한 인가 정책이 부재하면 서비스는 접근을 거부한다. 이때 발생하는 인가 오류를 네트워크 단절로 오인하여 불필요한 인프라 점검에 공수를 낭비하는 관제 병목이 발생한다.

사내 공개 서비스를 내부망에 방치한 채 도면상에만 DMZ 라벨을 부여하는 안티패턴 역시 심각한 보안 사각지대를 형성한다. 외부 방문자에게 웹 서비스를 개방하면서 웹 서버를 직원용 스위치에 그대로 연결하면, 웹 취약점을 통해 서버가 장악되었을 때 내부 업무 단말로의 횡적 이동을 통제할 물리적 검문소가 사라진다.

기업 외부망으로 통하는 에지 라우터와 인터넷 회선이 단일 경로로 구성된 환경에서는 회선 절단이나 포트 장애가 곧바로 전사 업무 마비로 직결된다. 직원의 외부 업무 트래픽과 외부 방문자의 DMZ 유입 트래픽이 동일한 물리 링크를 공유하므로, 단일 실패점으로 인한 가동 중단 위험이 상존한다.

네트워크 전송 품질 진단에 있어서도 ICMP 기반 왕복 시간 측정과 단순 홉 추적에 의존하는 기존 방식은 한계를 드러낸다. 3계층 패킷 왕복 시간이 양호하더라도 애플리케이션 계층의 렌더링 지연이나 서버 처리 병목을 식별할 수 없어 장애 원인 규명에 혼선을 초래한다.

## 4. 엔지니어링 의사결정 및 리팩터링

### 4.1. 클라우드 책임 공유 모델과 인프라 형태별 관리 경계 구분

인프라 서비스 모델을 IaaS, PaaS, SaaS의 3대 범주로 명확히 분류하고, 각 계층에서 제공자와 기업이 분담해야 하는 엔지니어링 책임을 확립했다. 물리적 서버가 시야에서 사라졌다고 해서 시스템 관리 작업이 소멸하는 것은 아니며, 추상화 수준에 따라 관리 주체만 이동한다.

IaaS 환경에서는 가상 머신과 가상 네트워크가 제공되지만 운영체제 설치, 커널 패치, 방화벽 포트 개방, 서비스 배포는 온전히 이용 기업의 과업이다. 반면 PaaS는 런타임 플랫폼 관리를 제공자가 전담하므로 기업은 소스코드와 데이터 연결에 집중할 수 있다.

소프트웨어 기능 자체를 소비하는 SaaS 모델에서도 이용자 계정 발급, 직무별 인가 권한 설정, 공유 범위 통제는 전적으로 기업의 거버넌스 영역이다. 다중 인증을 통해 신원 검증을 통과한 사용자라도 세부 문서 편집 인가가 부여되지 않으면 기능이 제한된다.

```text
인증: 사용자의 신원을 확인하는 단계 (다중 인증 완료)
인가: 검증된 신원에 자원 접근 및 수정 권한을 부여하는 단계 (문서 편집 권한)
결과: 신원이 입증되어도 편집 인가가 없으면 서비스 거부 반환 (네트워크 단절이 아님)
```

접속 환경에 따른 트래픽 경로 분기 정책도 명확히 규정했다. 사내 직원의 외부 SaaS 요청은 사내 방화벽을 통과하여 인터넷으로 직접 라우팅되지만, 재택 직원의 경우 일반 인터넷을 통해 SaaS에 접속하고 사내 급여 시스템 접근 시에만 회사 VPN 터널을 경유하도록 이원화했다.

Rpg-sync 프로젝트에서 GCP 가상 머신 인스턴스를 프로비저닝하여 배포 환경을 구축했던 경험 역시 이러한 책임 경계와 직결된다. 클라우드 콘솔에서 클릭 몇 번으로 기본 Debian 이미지가 세팅된 가상 서버를 즉시 확보할 수 있었지만, 이는 IaaS 계층의 기반 자원을 임대한 것에 불과했다.

운영체제 환경 내의 사용자 권한 격리, 애플리케이션 서비스 데몬 설정, 클라우드 가상 사설망 방화벽 규칙을 통한 불필요한 포트 차단은 온전히 직접 엔지니어링해야 할 영역이었다. 기반 환경이 손쉽게 제공된다고 해서 시스템 보안과 권한 거버넌스의 책임까지 제공자에게 넘어가는 것은 아님을 명확히 체감했다.

### 4.2. DMZ 세그멘테이션과 방화벽 인터페이스 기반 최소 권한 통제

기업의 장비 관리 범위와 네트워크 신뢰 경계를 명확히 분리하여 DMZ 세그멘테이션 아키텍처를 설계했다. 에지 라우터는 외부 인터넷 방향에 위치하더라도 기업이 소유하고 관리하는 장비이며, 외부 SaaS는 관리 범위 밖이지만 안전하게 허용해야 하는 신뢰 대상이다.

논리 구성도 상의 단일 선이 물리적 단일 케이블을 의미하지 않는다는 점에 착안하여, 실제 물리 포트와 배선 규격을 1:1로 매핑했다. 스위치를 경유하는 연결에는 Straight-Through 케이블을 사용하고, 라우터와 방화벽 간 직결에는 Cross-Over 케이블을 배치하여 물리 계층 신호 전달을 확립했다.

공개 웹 및 DNS 서비스를 제공하는 DMZServer는 내부 업무용 Switch0이 아닌, Firewall0의 독립 인터페이스 Port 1/3에 직결했다. 이를 통해 외부 방문자의 접근 경로와 내부 직원의 업무 경로를 물리적 인터페이스 레벨에서 완전히 격리했다.

```text
[외부 방문자 Inbound 흐름]
OutsidePC -> Router1 -> Router0 -> Firewall0(Port 1/1) -> Firewall0(Port 1/3) -> DMZServer (웹 접속 허용)

[DMZ 침해 시 내부망 횡적 이동 차단]
DMZServer -> Firewall0(Port 1/3) -> [방화벽 정책 드롭] -X-> Firewall0(Port 1/2) -> Switch0 -> 직원 PC (차단)
```

방화벽 정책은 엄격한 비대칭 최소 권한 원칙을 강제했다. 외부 방문자가 DMZ 서버의 웹 포트로 인입하는 트래픽은 허용하되, DMZ 서버에서 내부 직원망으로 시작되는 모든 신규 세션 요청은 방화벽 규칙에 의해 즉각 폐기되도록 구성했다.

웹 서버에 침해가 발생하더라도 공격자가 DMZ 구역을 벗어나 내부 업무 단말로 악성코드를 전파하거나 횡적 이동을 시도할 수 없다. 단순한 명칭 부여가 아닌 방화벽 인터페이스 단위의 물리적 분기만이 실효적인 격리 경계를 형성한다.

### 4.3. 네트워크 전송 품질 진단의 허실과 종단 간 병목 분석

네트워크 장애 관제 시 흔히 범하는 오류인 표기 대역폭과 실제 처리량의 혼동을 실증적으로 규명했다. 물리 회선이 1Gbps 대역폭을 제공하더라도 원격 서버 애플리케이션이 5MB/s로 전송률을 제한하고 있다면, 클라이언트가 체감하는 속도는 서버의 상한선인 40Mbps에 묶인다.

네트워크 회선 대역폭은 파이프의 직경에 불과하며, 종단 간 실제 처리량은 경로 상의 가장 좁은 병목 구간과 애플리케이션 계층 전송 정책에 의해 결정된다. 단순 회선 증설로는 애플리케이션 계층의 전송 캡을 해결할 수 없다.

ICMP 기반 ping 응답 시간이 지닌 진단적 한계도 상세히 분석했다. 왕복 시간은 요청 이동, 대상 장비의 패킷 처리, 응답 반환 이동의 총합이므로 양방향 경로가 비대칭일 경우 편도 시간을 단순 1/2로 단정할 수 없다.

ping 응답이 20ms로 신속하더라도 웹 브라우저 화면 렌더링에 수 초가 소요될 수 있다. DNS 조회, TCP 3-Way Handshake, TLS 암호화 협상, 백엔드 데이터베이스 쿼리 연산, DOM 렌더링 등 L7 상위 계층의 복합적 지연 요소를 ping 도구로는 감지할 수 없다.

```text
[tracert 점증 TTL 메커니즘]
프로브 1: IP TTL=1 전송 -> 홉 1 라우터에서 TTL 만료 -> ICMP Time Exceeded(Type 11) 수신 (홉 1 RTT 기록)
프로브 2: IP TTL=2 전송 -> 홉 1 통과, 홉 2 라우터에서 TTL 만료 -> ICMP Time Exceeded 수신 (홉 2 RTT 기록)
중간 타임아웃(*): 해당 홉 라우터가 ICMP 에러 메시지 생성을 비활성화했거나 방화벽이 차단한 상태
최종 목적지 도달: 중간 타임아웃과 무관하게 패킷 전달 경로는 정상 작동 중임을 입증
```

tracert 경로 추적에서 중간 홉이 타임아웃(`*`)을 반환하더라도 최종 목적지가 정상 응답한다면 네트워크 전달 경로는 완전히 건전하다. 중간 장비의 ICMP 응답 생성 정책과 실제 패킷 포워딩 기능은 별개의 영역이므로, 섣부른 장애 판정을 배제해야 한다.

이러한 물리적 전송 지연과 애플리케이션 계층 체감 성능의 괴리는 rpg-sync 프로젝트에서 미국 리전 클라우드 인스턴스와 한국 리전 데이터베이스를 연동할 때 뼈아프게 직면했던 병목이었다. 태평양을 건너는 물리적 거리로 인해 왕복 지연 시간이 200ms 이상 치솟았고, 웹 화면에 표시할 데이터를 매 요청마다 데이터베이스에서 동기 조회하면서 전체 페이지 렌더링이 멈칫거리는 사용자 경험 저하를 겪었다.

화면 깜빡임을 완화하기 위해 스켈레톤 UI를 도입하고 직업 리뷰 로직에 낙관적 UI를 적용해 클라이언트 체감 지연을 줄이고자 시도했으나, 이는 표면적인 시각적 보완에 불과했다. 매 요청마다 태평양을 왕복하는 네트워크 비용과 데이터베이스 커넥션 부하라는 근본 문제는 해소되지 않았다.

결국 데이터베이스로 향하는 반복 조회를 원천 차단하기 위해 Redis 캐싱 레이어를 도입하여 지연 시간을 단축했다. 오늘 실습에서 규명한 물리 회선 대역폭과 애플리케이션 실효 처리량 간의 괴리, 그리고 ICMP 왕복 시간과 상위 계층 지연 요인의 분리 원리가 당시 아키텍처 의사결정의 기술적 배경이었음을 명확히 정립할 수 있었다.

### 4.4. 관리 거리를 활용한 부동 정적 라우트 기반 회선 이중화

단일 회선 장애로 인한 서비스 단절을 방지하기 위해, 예비 라우터 Router2를 추가하고 관리 거리를 차등 적용한 부동 정적 라우트 토폴로지를 구축했다. 라우팅 프로토콜이나 정적 경로의 신뢰도를 결정하는 관리 거리 메커니즘을 활용하여 무중단 장애 조치 환경을 완성했다.

세 라우터를 삼각형 메시 구조로 연결하고, 신규 링크에 각각 /30 전용 서브넷을 할당했다. Router0의 G0/2 포트 10.0.0.5/30과 Router2의 G0/0 포트 10.0.0.6/30, 그리고 Router1의 G0/2 포트 10.0.0.9/30과 Router2의 G0/1 포트 10.0.0.10/30을 상호 결속했다.

주 경로와 예비 경로 간의 충돌을 방지하고 자동 전환을 유도하기 위해 관리 거리를 정밀하게 설계했다. 동일 목적지에 대해 복수의 정적 경로가 존재할 때, 라우터는 관리 거리가 낮은 경로만을 활성 라우팅 테이블에 등록한다.

```cisco
Router0(config)# ip route 172.20.10.0 255.255.255.0 10.0.0.2
Router0(config)# ip route 172.20.10.0 255.255.255.0 10.0.0.6 10
```

Router0에서 외부 제공자망 172.20.10.0/24로 향하는 기본 주 경로는 기본 관리 거리인 1로 설정하여 평시 트래픽을 처리하도록 했다. 반면 예비 라우터 10.0.0.6을 경유하는 백업 경로는 관리 거리를 10으로 지정하여 부동 정적 경로로 대기시켰다.

외부 라우터인 Router1에서도 사내망으로 돌아오는 응답 트래픽을 위해 역방향 예비 경로를 대칭적으로 구성했다. 내부 직원망 192.168.10.0/24와 공개 DMZ 192.168.20.0/24 모두에 대해 예비 라우터 10.0.0.10 경유 경로를 관리 거리 10으로 사전 배치했다.

```cisco
Router1(config)# ip route 192.168.10.0 255.255.255.0 10.0.0.10 10
Router1(config)# ip route 192.168.20.0 255.255.255.0 10.0.0.10 10
```

중간 예비 전송을 담당하는 Router2에는 사내 직원망과 DMZ 트래픽을 Router0(10.0.0.5)으로 넘기고, 외부 제공자망 트래픽을 Router1(10.0.0.9)으로 넘기는 정적 포워딩 규칙을 등록했다.

```cisco
Router2(config)# ip route 192.168.10.0 255.255.255.0 10.0.0.5
Router2(config)# ip route 192.168.20.0 255.255.255.0 10.0.0.5
Router2(config)# ip route 172.20.10.0 255.255.255.0 10.0.0.9
```

평상시 Router0의 라우팅 테이블에는 관리 거리 1의 주 회선 10.0.0.2만 표출되며, 백업 경로는 숨겨져 대기한다. 주 회선 물리 인터페이스에 장애가 감지되는 즉시 라우터 운영체제는 주 경로를 라우팅 테이블에서 퇴출시키고 관리 거리 10의 백업 경로를 즉각 승격시킨다.

## 5. 검증 및 회고

### 5.1. 네트워크 세그멘테이션 및 무중단 장애 복구 실증 검증

구축한 네트워크 아키텍처의 유효성을 검증하기 위해 세 가지 핵심 시나리오에 대한 실증 테스트를 수행했다.

첫째, 방화벽 기반 DMZ 격리 정책을 검증했다. 외부 방문자 단말인 OutsidePC에서 DMZServer의 웹페이지(192.168.20.10:80) 및 DNS 서비스로 요청을 송신한 결과, 정상적인 웹 응답 페이지가 수신되었다. 반면 DMZServer에서 사내 업무 단말인 PC0(192.168.10.10)으로 시도한 모든 역방향 신규 연결은 Firewall0의 접근 통제 규칙에 걸려 전량 드롭되었다.

둘째, 정상 상태에서의 주 회선 트래픽 경로를 확인했다. Router0과 Router1에서 라우팅 테이블을 조회한 결과, 관리 거리 1의 직결 주 경로(`10.0.0.0/30`)만이 활성 라우트로 표출되었으며, 사내 PC0에서 외부 WebServer(172.20.10.10)로의 HTTP 트래픽이 주 회선을 경유하여 지연 없이 왕복함을 확인했다.

셋째, 주 회선 단절 상황에서의 부동 정적 라우트 장애 조치를 검증했다. Router0의 주 회선 인터페이스인 GigabitEthernet 0/1을 관리자 명령으로 강제 종료(`shutdown`)시켰다.

```cisco
Router0(config)# interface gigabitethernet 0/1
Router0(config-if)# shutdown
Router0(config-if)# end
```

인터페이스 다운 직후 Router0의 라우팅 테이블을 재조회한 결과, 기존 관리 거리 1의 경로가 즉시 제거되고 대기 중이던 관리 거리 10의 예비 경로(`via 10.0.0.6`)가 라우팅 테이블에 즉각 등록되었다.

```text
Router0# show ip route
Gateway of last resort is not set
      10.0.0.0/8 is variably subnetted, 4 subnets, 2 masks
C        10.0.0.4/30 is directly connected, GigabitEthernet0/2
C        10.0.0.12/30 is directly connected, GigabitEthernet0/0
S     172.20.10.0/24 [10/0] via 10.0.0.6
S     192.168.10.0/24 [1/0] via 10.0.0.14
S     192.168.20.0/24 [1/0] via 10.0.0.14
```

Router1에서도 외부 방문자의 DMZ 접속 경로가 예비 라우터(`via 10.0.0.10`)로 자동 전환되었다. PC0의 외부 웹 포털 브라우징과 OutsidePC의 사내 DMZ 웹 서비스 접속 모두 회선 단절 상태에서도 세션 중단 없이 정상 유지됨을 실증했다.

### 5.2. 현실적 회고 및 교훈

클라우드와 네트워크 인프라를 연계하면서 얻은 가장 큰 교훈은 과거 프로젝트에서 맞닥뜨렸던 성능 병목과 문제 해결의 순간들이 네트워크 기본 원리와 긴밀하게 맞닿아 있었다는 사실이다. 프로젝트에서 미국 리전 서버와 한국 데이터베이스 간의 200ms 지연을 해결하기 위해 UI 트릭을 거쳐 결국 Redis 캐싱을 도입했던 고투의 원인이, 오늘 분석한 물리적 대역폭과 애플리케이션 실효 처리량의 괴리에서 비롯되었음을 이론과 실습으로 명확히 규명할 수 있었다.

GCP 가상 머신을 띄우며 마주했던 클라우드 인프라 역시 물리 장비 관리만 사라졌을 뿐, 운영체제 내부의 세부 권한 통제와 방화벽 인바운드 정책은 전적으로 엔지니어의 몫이라는 책임 공유 모델의 본질을 실감했다. 인증 성공이 곧 올바른 업무 권한을 의미하지 않으며, 단말 간 3계층 패킷 통달이 상위 애플리케이션의 온전한 동작을 보장하지 않는다는 사실을 확인했다.

부동 정적 라우트를 실습하면서 단 두 줄의 관리 거리 설정만으로 복잡한 라우팅 프로토콜 없이도 견고한 무중단 장애 조치 체계를 완성할 수 있음을 체감했다. 서비스의 연속성을 보장하는 고가용성 아키텍처는 거창한 솔루션의 도입이 아니라, 기본 네트워크 메커니즘을 정확히 이해하고 대칭 경로를 꼼꼼히 설계하는 것에서 출발한다.
